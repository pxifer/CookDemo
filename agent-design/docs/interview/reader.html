项目讲述：一顿可做的饭，怎样连接公共知识与模型

1. 30秒和3分钟怎样讲

30秒：拾味是菜谱推荐应用。用户给疾病或减脂/增肌目标、本餐食材及过敏忌口，系统从已发布的实际菜谱中选出可做的菜，并说明当前能对应的食材/做法依据。程序管资格、限制和证据归属，模型在受控候选中做语言与选择。疾病RAG目前是本地研究接入，未完成专业签认或正式疾病发布。

3分钟：最初证据问答回答的是“某指南怎么说”，与用户要的“今晚做哪几道菜”有距离。改进不是继续堆向量，而是补齐疾病/目标→条件化食物指导→明确目录食材/主做法→真实配方的关系。疾病与训练/体重目标分开；定性选菜不普遍要求身高体重，也不能凭成分机制推导新的食物疗效。先筛硬条件和有效避免，再选菜，再复核整餐和最新资料。没健康映射的合格普通菜可以推荐，但保留健康判断。真实模型曾无依据拒绝普通菜、又给别的菜挂错引用，促成了提示词收缩和程序绑定依据。研究链另保留A1/向量/RRF用于技术比较，效果和未完成项分别报告。

  1. 输入：“我是成年人，我有高脂血症，我想减脂”；白菜500g、豆腐500g、1人、不补买。疾病和目标分别保存。本例无过敏设置，不假称一单验证所有过敏场景。
  2. 指导：直接取18条指导、7条证据；检查条件与映射。不是向量top-18。血脂分型未知只限制相关内脏指导，不挡无内脏菜。

  4. 增强：只带候选实际关联的6条指导、3条原文，加完整配料/主与备选做法、本餐、数量类别、scope、locked。不是整库拼接，也不是只给食材名称。

Q006 · 怎样证明比直接聊天更有价值？

状态：有工程与少量真实样例；缺独立业务对照

Q020 · RRF原理及公式中的60是什么？

状态：研究两层RRF已实现

  • 口述：RRF把不同通道的名次转成倒数分再求和，避开原始分数量纲不一致。一般为Σw/(c+rank)，缺席通道贡献0；c越大，头部相邻名次差距越缓。
  • 实现/参数：A1内部实体/词面等权；外层为2/(60+r_A1)+1/(60+r_dense)。60是平滑常数，不是召回数量或top-k。
  • 为什么/比较：方法有论文依据，当前2:1偏重可控A1是工程初值；没有证明本项目最优。
  • 难点/追问：融合不判断事实是否真实或条件是否适用；两路都偏题时仍会把偏题事实排高。

依据：E06、S01。

Q059 · Attention和Transformer至少讲到哪？

状态：基础理论；未训练模型

  • 难点/追问：追问时讲清表示与注意力权重不等于事实依据；不编造供应商内部架构或推理链。

  • 难点/追问：“不建议高钾”与“建议高钾”词义接近，向量可能很近；否定、条件与支持关系仍必须单独核对。

Q082 · 取消、超时、429和未知供应商状态怎么处理？

依据：E09、E10。

真实问题、解决过程与可讲的亮点

以下是项目记录中的事件，不是为了面试编出的“踩坑故事”。本人参与程度、提交和验证应据实说明；历史检查数量不当作本手册新跑的测试。

1. 证据问答偏离“今晚吃什么”

触发：用户想按疾病/减脂和现有食材选菜，而证据问答只会复述指南。原因：知识终点停在营养成分和问答，缺少食物对象、适用条件和实际配方桥梁。改进：增加直接食物/工艺指导，疾病与目标分开，用受控成员和真实主做法绑定目录，再复用资格程序。成分机制保留作解释，不自动变成食物获益。证据：业务计划与实施、真实例子。局限：映射不是全目录覆盖，尚不能输出全天营养处方。

口述：“最大的调整是把技术闭环改成用户闭环：检索出一段话还不够，还要能说明它关联哪项食材、哪道实际配方，以及哪些地方仍未知。”

2. 合格的小葱拌豆腐被模型拒选

触发：第2次真实调用，程序有合格普通菜，模型因油量未知、推测与减脂冲突而返回空选择。原因：把缺依据、少选和硬避免混在一起；提示词给模型过大的医学否决权。修复：无映射不全局禁普通菜；少选只排序/提醒；目录已硬筛，不能凭未提供的营养判断拒绝唯一合格候选。验证：第3次该普通菜真实返回，健康判断保留。局限：单例证明缺陷修复，不是全部模型拒选率对照。

口述：“不是让模型更敢推荐，而是把无依据的地方缩成未知，让代码负责可验证的条件，避免AI自己新增禁忌。”

3. 模型拿真实证据ID挂给不匹配的菜

触发：第4次调用给白菜心挂错引用，程序拒绝；ID存在但该配方没有映射。原因：让模型同时选菜、解释和声明来源归属，结构合法仍可能语义错配。修复：模型只交目录ID和本餐理由；程序按真实配料、主做法和支持/限定绑定。研究业务不发布自由健康summary/reason。验证：第5次3菜有真实回执，输出1道有据、2道保留健康判断。局限：研究问答自由claim仍需独立蕴含/专业评测。

口述：“我们没有靠第二个Prompt让模型自己证明，而是收回引用权限，把它变成程序可检查的配方关系。”

4. 旧导航引用被唯一同名正文“洗白”（RAG-005 P2）

触发：资料重建时，旧引文来自导航；新正文恰有唯一同名内容，定位恢复提前成功，绕过旧来源角色核验。发现：管理审核端到端调用builder复现，不只测帮助函数。修复：任何迁移/重定位前先审旧定位来源，导航仍隔离；唯一正文也不自动批准。验证：修复已复审并合入main，见管理审核及定位治理。局限：旧冻结知识/向量没有因此被自动重整替换。

口述：“hash和字面唯一只能说明定位候选，不能证明原先引用正确。这里暴露的是校验顺序问题，我们把来源核验提到了所有快捷路径之前。”

5. 表格看似抽出来，实际对象—值可能错位

现象：无竖线表宽列漏分、上下标数字错序、跨列串文；旧短摘有的只剩表号。方法：保留词框/字号，修订上下标与列界、按物理格输出；表题、表头路径、单位、脚注单独关联候选；原词守恒和回查检查。证据：表格/OCR记录、v3治理。局限：322表/14214格/7510关系候选不是审核通过的营养事实，OCR一致不是准确率。

口述：“PDF转出文字不是结束。营养表必须知道哪个数属于哪个对象、单位和限定，否则整齐的JSON也会保存错误。”

6. 建了向量，指标却不如A1

事实：研究27题的A1已达Recall@10/MRR=1；两模型hybrid Recall相同、MRR未优于A1。解释：小而受控的库、明确实体和已曝光调试题有利于A1；向量相近不一定对象/限定一致。处理：保留基线，报告无增益；业务直接指导不强行使用向量。待做：独立难题、否定/别名、无答案和跨来源条件，固定其他变量消融。不能为了漂亮结论修改gold或删除失败题。

口述：“我验证了向量通路，但没有把‘用上向量’等同于收益。真实业务仍用更可控的直接指导，等独立数据证明需要再接。”

7. 建议列表被大类别占满、补问过泛

原因：同一蔬菜类有多个成员，按固定遍历取前20挤掉其他方向；不相关条件也问用户。修复：avoid/limit/prefer方向轮转，再按主题/对象分配；仅对相关且可映射指导问明确条件，允许不清楚。证据：质量治理记录。局限：轮转是覆盖策略，没有证明用户满意度提升或已学到最优排序。

8. 迟到请求把旧Key或疾病状态带回来

风险：发起时合法，返回时用户已清空Key、删病或改食材。方法：当前档案为准、operation/输入/版本绑定、返回前再核验；图片读取/上传也检查最新会话和Key，不能换供应商偷偷续跑。证据：账户及限制规则、照片入口专项。局限：本地延迟供应商回归不等于真实供应商收到取消就不计费。

2. 把RRF和分数标定讲明白

RRF(f) = Σ通道 w通道 / (c + rank通道(f))
rank从1开始；缺席贡献0；当前研究外层w_A1=2、w_dense=1、c=60。
A1内部还把实体路、词面路等权融合；两层不要混为一次。

RRF解决不同检索分数不在同一量纲的问题，使用名次较容易组合。它损失绝对分差信息，不能识别事实真假或自动消除偏题。c大时相邻头部差距更平；不是“c大就更重视第一名”。对A1第1、dense第10的同一事实，当前外层是 2/61+1/70≈0.047073；等权才是 1/61+1/70≈0.030679。

替代方案是将分数归一化/校准后加权、学习排序或cross-encoder；需要足够标注和跨版本稳定性。min-max受候选极值影响，z-score依赖分布；不能仅因为麻烦就断言都比RRF差。RRF原论文是方法依据，其数据集不替本项目证明60最优。

测试正常JSON、围栏JSON、截断JSON、重复键和“结构正确但目录外ID”。演示解析层拒绝非JSON和重复键；之后验证结构、ID及去重。不要用 \{.*\} 抽取任意第一/最后大括号，也不要修补半条付费响应后假装完整成功。

当前项目采用严格JSON与完整终态门禁，并非用本练习Python代码处理线上输出。若未来允许外层代码围栏，必须显式限定完整唯一围栏、保留原文和解析状态，业务复核仍不能省略。

额外场景：小模型压缩与大量工具

小模型做摘要可能便宜、快，但并非天然不会丢健康条件；先用结构化限制表保存不可变约束，再比较不同模型的保留率、纠错和成本。当前没有小模型摘要服务。工具过多可先按任务与权限检索工具目录，再注入少量相关Schema；返回数据用字段选择、分页或受控引用读取，不能靠模型自行丢掉单位/限定。当前也没有动态工具检索平台。

同一个资料的排名不是永久固定：相同索引、同一query向量和排序规则下精确距离可复算；问题、规范化、条件、知识/模型版本变化会改变距离或资格。不能为让某条“权威资料”每次第一而固定加分，先确定它是否真的支持当前任务。

1. 切块的实际实现：没有配置512-token滑窗

1.1 当前到底怎样切

  1. 冻结v2的98条证据由两代构建脚本整理，标记proposition-v1。脚本事先写明来源、页/章节、起始原文、可选结束原文及整理摘要，再从规范化文本中摘取相应范围。
  2. 没有结束锚点时，只摘取起始字符串本身；有结束锚点时，从起点取到随后第一个结束锚点。PDF操作限定在指定物理页，不能自动跨页补齐；视觉证据是指定图像区域的目视短摘。旧构建器用find选锚点，并不是通用语义边界识别器，旧导航误引正是需要修正的真实缺陷。
  3. 所谓“命题级”是整理意图和版本标签，不是已经实现自动命题抽取或经过比较选出的语义切块算法。内容由脚本明确整理，不是LLM自动抽取整库事实。
  4. 没有统一chunk_size、目标token长度、最小语义长度或滑窗overlap。Schema仅要求originalSpan非空，没有切块长度上限；后续Embedding接口有输入保护限制，两者不能混称。
  5. 没有滑窗重叠参数不表示原文区间绝不重叠：在可比较的同源/同页/同规范化偏移中，实测有1对重叠（dm-carbs与dm-low-gi）。视觉引用不能靠字符偏移计算重叠。
  6. 实际向量化的是retrievalText。继承v1的53条为章节 + 空格 + 摘要 + 空格 + 原文，v2新增45条为摘要 + 空格 + 原文。没有把这两种格式重新统一，也没有验证加章节/摘要一定更好。
