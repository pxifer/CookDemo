<a id="q001"></a>
### Q001 · 一句话介绍项目，解决什么问题？

状态：**业务已实现；疾病RAG本地研究**

- **口述**：拾味把用户的疾病或饮食目标、现有食材、过敏忌口等条件，转成真实目录中的可做菜品，并给出能追溯的食材或做法依据。重点是把资料变成一次可执行的本餐选择。
- **实现/参数**：程序负责目录资格、限制和整套复核，模型在合格候选中选ID；普通推荐、个人Key功能和本地疾病RAG的发布范围分别说明。
- **为什么/比较**：价值是实际配方、用户条件和来源的一致性；尚无独立用户满意度或医学有效性对照。
- **难点/追问**：追问“是不是推荐得更健康”时，只说当前验证到的条件检查与依据归属，不承诺疗效。

依据：[E01](sources-and-coverage.md#e01)、[E08](sources-and-coverage.md#e08)。

<a id="q002"></a>
### Q002 · 为什么需要RAG，长上下文和微调能否替代？

状态：**架构取舍；未做三者效果横评**

- **口述**：RAG适合频繁更新、必须追出处和撤回的公共知识。少量资料可先用全文作基线；微调主要改变稳定行为，不能直接替代来源版本与权限控制。
- **实现/参数**：本项目事实、原文证据、版本和规则分层，研究链检索后生成，业务链读取直接指导；没有做模型微调。
- **为什么/比较**：选型来自可维护、可追溯的需求，不能说已经实验击败“全文＋大模型”或微调。
- **难点/追问**：若全文基线已满足要求，保留简单方案；资料少不代表需要复杂向量平台。

依据：[E02](sources-and-coverage.md#e02)、[E06](sources-and-coverage.md#e06)、[S01](sources-and-coverage.md#s01)。

<a id="q003"></a>
### Q003 · 大模型负责什么，哪些事交给程序？

状态：**业务已实现**

- **口述**：模型读本餐条件、真实配料和做法，在提供的catalog里选择菜品并写本餐说明。身份、过敏忌口、可行性、引用归属和是否能返回结果由代码判断。
- **实现/参数**：模型不能改用户档案、忽略限制、执行SQL、编造菜谱ID或发布健康规则；健康依据按真实配方由程序绑定。
- **为什么/比较**：模型擅长语言与偏好组合，确定性规则更适合硬限制；没有“模型一定比规则差”的全任务比较。
- **难点/追问**：模型说“已经校验”不构成证明；代码还须重新核对当前输入和版本。

依据：[E08](sources-and-coverage.md#e08)、[E09](sources-and-coverage.md#e09)、[E11](sources-and-coverage.md#e11)。

<a id="q004"></a>
### Q004 · 为什么没有使用LangChain或LlamaIndex？

状态：**当前编排已实现；框架未横评**

- **口述**：当前链路有限、业务约束较多，使用TypeScript普通函数与清晰适配接口，便于定位失败、控制调用和测试。没有把框架状态当成健康事实。
- **实现/参数**：EmbeddingProvider、向量存储和Generator可替换；Python运行本地Embedding，PG存储知识。仍复用了模型库、数据库和Schema工具。
- **为什么/比较**：取舍是当前复杂度与可控性，不是从零造所有底层，也没有证明手写性能更优。
- **难点/追问**：连接器、恢复或图流程复杂后可以再评估框架；能解释状态和边界比框架名更重要。

依据：[E05](sources-and-coverage.md#e05)、[E06](sources-and-coverage.md#e06)、[E18](sources-and-coverage.md#e18)、[S06](sources-and-coverage.md#s06)。

<a id="q005"></a>
### Q005 · RAG怎样和推荐系统打通，白板怎么画？

状态：**业务与研究两条链分开**

- **口述**：画“疾病/目标→适用指导→明确食材/工艺映射→真实配方硬筛→增强模型选ID→程序整餐复核→依据与未知说明”。另画独立问答的A1/向量/RRF支路。
- **实现/参数**：当前业务选菜不调用dense/hybrid；新清洗结构块也未替换旧知识与索引。两条支路不能画成全部已经串联。
- **为什么/比较**：直接食物指导能落到系统配方，研究问答跑通本身不能代表推荐闭环完成。
- **难点/追问**：追问向量在哪生效时，明确回答在研究证据问答支路；不要用规划架构冒充运行架构。

依据：[E01](sources-and-coverage.md#e01)、[E06](sources-and-coverage.md#e06)、[E08](sources-and-coverage.md#e08)。

<a id="q006"></a>
### Q006 · 怎样证明比直接聊天更有价值？

状态：**有工程与少量真实样例；缺独立业务对照**

- **口述**：可以展示同一输入下，系统只返回真实菜谱、保留过敏和补买条件，并能回查实际配料与出处。直接聊天通常没有当前目录和账户状态。
- **实现/参数**：真实例子中模型选择3道菜，程序区分1道有当前依据、2道保留健康判断；没有说三道都经疾病适宜性验证。
- **为什么/比较**：这证明可执行性与可追溯性的一次样例，不证明总体回答准确率更高；公平A/B仍需同题同资料同预算。
- **难点/追问**：演示失败样例和“不知道”，比宣称比通用模型全面更强更可信。

依据：[E08](sources-and-coverage.md#e08)、[E13](sources-and-coverage.md#e13)、[E14](sources-and-coverage.md#e14)。

<a id="q007"></a>
### Q007 · 最大的局限是什么，预算增加先做什么？

状态：**已知缺口与后续设计**

- **口述**：当前瓶颈是直接指导和目录映射覆盖、原文支持关系、清洗候选接入，以及独立质量评测。向量或重排模型再大，也无法替代不存在或错误的证据。
- **实现/参数**：先重整已发现误引与必要限定，建立新知识/索引版本，再按失败分布补目标和食材覆盖。
- **为什么/比较**：新增预算优先投可核验数据、适用性复核与真实任务反馈；暂不承诺购买某GPU或训练平台的收益。
- **难点/追问**：若问给十万具体怎么花，讲阶段验收与止损点，不编造报价和未经测试的提升百分比。

依据：[E02](sources-and-coverage.md#e02)、[E14](sources-and-coverage.md#e14)、[E15](sources-and-coverage.md#e15)。

<a id="q008"></a>
### Q008 · 资料如何收集、清洗，表格和跨页怎么办？

状态：**离线治理工程已实现；语义审核未完成**

- **口述**：登记来源、版本和hash，再分HTML、电子PDF、扫描页处理。DOM识别正文，PDF保留词框/字号；表格按格而非一串文字保存，脚注、单位和否定要保护。
- **实现/参数**：有13来源/479单元的治理记录；续表需相邻页、同表号及列界匹配，当前不自动批准继承表头；OCR保留原图坐标和待核状态。
- **为什么/比较**：有具体失败修复和重复构建，没有独立全库解析准确率，也没横评所有OCR引擎。
- **难点/追问**：“抽到了数字”不等于对象—值—单位对应正确；不能用模型常识补缺失字段。

依据：[E03](sources-and-coverage.md#e03)、[E04](sources-and-coverage.md#e04)、[E14](sources-and-coverage.md#e14)。

<a id="q009"></a>
### Q009 · 为什么把Fact和Evidence分开？

状态：**研究库已实现**

- **口述**：Evidence说明原文说了什么、在哪里；Fact是整理后的对象、关系、方向及条件。一个事实可以依赖多个支持与限定证据，一段证据也可能支撑不同事实。
- **实现/参数**：原文、摘要、检索文本、来源hash分别保留；引用通过稳定ID关联，事实不覆盖原件。
- **为什么/比较**：分层利于更新、撤回和审计，不表示事实天然正确，也不是实现了GraphRAG。
- **难点/追问**：同一短摘出现不能证明蕴含整条事实；已发现导航问句误作支持，必须重整依赖关系。

依据：[E02](sources-and-coverage.md#e02)、[E15](sources-and-coverage.md#e15)。

<a id="q010"></a>
### Q010 · 事实怎样提取，如何防止事实幻觉？

状态：**当前脚本整理；无通用LLM自动入库**

- **口述**：现有事实主要由脚本显式整理，配合源文定位和条件，不是让大模型自由读全文后直接入库。新清洗产物首先是候选，尚未自动产生正式新事实。
- **实现/参数**：Schema和代码检查实体类型、方向、证据/版本关联；`source_checked`是项目核对，不能冒充独立专业审核。
- **为什么/比较**：若以后用LLM抽取，先生成带原文span的候选，再核验限定、冲突与支持关系；模型不得自批。
- **难点/追问**：结构校验能发现缺字段或错引用，不能完全发现“原文其实没说这个结论”。

依据：[E02](sources-and-coverage.md#e02)、[E03](sources-and-coverage.md#e03)、[E14](sources-and-coverage.md#e14)。

<a id="q011"></a>
### Q011 · 原文更新或撤回，如何避免继续答旧知识？

状态：**版本/撤回机制已实现；新内容接入仍需新版本**

- **口述**：原件hash、来源版本、知识包和索引身份绑定。更新生成新版本，重新核对受影响事实与向量；撤回则先阻止继续使用，不等待模型重新训练。
- **实现/参数**：检索、生成前后和返回前检查撤回；个人结果游标也绑定知识/输入版本。当前不是任意网页变化后自动热更新整库。
- **为什么/比较**：不变版本和事务可防静默混库；效果与并发撤回测试、恢复测试的范围分开报告。
- **难点/追问**：光改显示日期或缓存TTL不能证明旧事实已失效；发布与回退须切换一致版本集合。

依据：[E02](sources-and-coverage.md#e02)、[E06](sources-and-coverage.md#e06)、[E10](sources-and-coverage.md#e10)。

### Q012 · 块怎样切、多大、Overlap多少，为什么？

状态：**旧短摘已实现；自动切块选型未完成**

- **口述**：当前98条采用脚本指定页/起止原文摘取，没有统一chunk_size和滑窗overlap；不是固定512 token。原文中位64字符，最长357；Qwen实际索引文本中位68、最长339 token。
- **实现/参数**：53条检索表示带章节/摘要/原文，45条带摘要/原文；8192是编码上限。可比较的旧原文引用有1对重叠，不能说全部overlap=0。
- **为什么/比较**：设计意图是保留命题和条件，但长度是摘录结果；没有128/256/512块长或0/32/64重叠的效果对比。
- **难点/追问**：部分短摘只有表号或导航级锚点，证明“命题级”标签不够；新清洗3717结构块未接入旧索引。

依据：[E02](sources-and-coverage.md#e02)、[E05](sources-and-coverage.md#e05)、[E14](sources-and-coverage.md#e14)。

<a id="q013"></a>
### Q013 · 怎么防止切断“除外、仅限、肾功能”等限定？

状态：**关系闭包已实现；自动边界识别仍局部**

- **口述**：不能只靠Overlap碰巧覆盖。将必要人群、否定、剂量或工艺条件显式保存在事实与限定证据关系中，选中事实时补齐其依赖。
- **实现/参数**：预算不够回退整条事实；必要条件未知则保留相关判断或补问，不能在模型里补成正常。
- **为什么/比较**：现有原词守恒和闭包回归防丢失，但不能证明所有旧短摘语义完整；跨页和表格限定仍待重整。
- **难点/追问**：给出“前段是建议、后段是例外”的构造例，检查两者是否共同进入最终上下文。

依据：[E02](sources-and-coverage.md#e02)、[E06](sources-and-coverage.md#e06)、[E07](sources-and-coverage.md#e07)。

<a id="q014"></a>
### Q014 · 知道哪些切块策略，项目适合哪种？

状态：**理论与候选方案，未完成公平横评**

- **口述**：固定字符/Token窗口便宜，递归切分兼顾段落标点，结构切分利用标题与表格；语义切分按内容变化；父子块用小块召回、带回较大上下文。
- **实现/参数**：现有是锚点短摘与结构候选；候选方向是结构优先、受token上限约束并关联表题/限定，不直接照搬产品默认。
- **为什么/比较**：应固定语料和任务比较边界完整性、召回、偏题、成本；没有哪种方法在所有文档都最优。
- **难点/追问**：小块相关不代表父块全部有用；父块扩展也必须受条件、权限和预算限制。

依据：[E03](sources-and-coverage.md#e03)、[E05](sources-and-coverage.md#e05)、[E18](sources-and-coverage.md#e18)、[S17](sources-and-coverage.md#s17)。

### Q015 · 6000 token上下文预算怎样来的？

状态：**研究工程初值，未做预算消融**

- **口述**：6000是研究上下文JSON的应用估算预算，不是Embedding块长，也不是模型上下文最大值。汉字按2、ASCII按0.4、其他按2估算并向上取整。
- **实现/参数**：最多8事实，逐条加入全部支持/限定；超限回退整条。该处未单独累加系统消息，真实生成usage另看供应商回执。
- **为什么/比较**：用于控制输入成本与噪声，没有3000/6000/9000对照证明6000最优。业务输入预算另为24000。
- **难点/追问**：工程估算不等于精确tokenizer；要区分输入、输出预留和完整请求的预算范围。

依据：[E07](sources-and-coverage.md#e07)、[E12](sources-and-coverage.md#e12)。
