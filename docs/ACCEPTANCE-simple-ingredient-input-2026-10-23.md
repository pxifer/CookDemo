# 简名食材匹配与真实页面验收

日期：2026-10-23。来源为用户要求“粉条”覆盖“土豆干粉条”，并对所有食材统一优化简名输入；对应[D13-07](technical/decision-log.md)。继承FR-02/03/05/07、主动补买、可选食材及硬限制规则。

## 本次修正

统一匹配入口使用标准ID/别名、显式大类和有边界的名称包含三层规则；名称包含对整个当前食材目录生效，不再只给粉条单独补别名。手动、文字、旧草稿、API确认及库存核对共用实现。例子包括粉条→土豆干粉条/红薯粉丝，猪肉→五花肉/猪里脊，香菇→鲜香菇，洋葱→黄洋葱，面粉→低筋面粉，蘑菇→金针菇/口蘑，豆腐→内酯豆腐，以及西蓝花→西兰花。

两字以上的名称包含保留方向性，不能因共享字符跨动物、食材来源或制品；负例覆盖土豆→土豆淀粉/土豆干粉条、花生→花生油、鱼→鱼丸、虾→虾皮、豆腐→日本豆腐、粉条→米粉、花菜→黄花菜等。单字“粉”和未知名称不自动匹配。非精确匹配不证明具体种类、形态或数量足够；运行时输入标识须经后端按同一名称和目录重建核验，也不作为已核验过敏/忌口对象。

发现并修正一个此前测试也错误认可的缺陷：原方数量为null时，没有该食材不应变成“未核实但可做”。现在缺少必需食材始终是missing，缺多少才是未知；未允许补买时排除，主动允许后明确标出“需补买；原方未注明用量”。已有食材但数量空白/不可比仍允许推荐并标未核实。

旧草稿中程序误造的“未分类：粉条”按完整历史特征识别，恢复为食材；正常过敏、忌口、未知限制及冲突保留。连续输入“面粉200g鸡蛋2个”额外覆盖通用食材后紧接精确食材的情况，不能把前一项用量吞掉或移给后一项。

## 实际验证

- 使用项目Node.js 24执行`scripts/run.ps1 build`：TypeScript及Vite通过。
- `scripts/run.ps1 test`：98项，97通过、0失败、1项可选真实PG用例因未设置启用变量跳过；本轮没有以此跳过项代替实际页面验收。
- 共享匹配表覆盖21组正例及18组负例，另核对文字连续输入、未知名称、伪造运行时标识、限制范围、原方未知量与旧草稿恢复。
- 真实数据库API：识别“面粉200g”后直接提交运行时输入，推荐返回200；伪造输入标识返回400 `INVALID_INGREDIENT`。构造数据库接口用例使用PGlite独立数据，不污染业务库。
- 真实4176业务服务＋现有Docker PostgreSQL：Edge桌面1440×1000和手机390×844共6项通过。手动输入“白菜、猪肉、粉条”且不允许补买时，推荐请求返回200并显示“白菜猪肉炖粉条”，不会混入实际缺少包菜、鸡蛋的“包菜炒鸡蛋粉丝”。文字只输入“粉条”，主动允许补买后，可列出相关粉条/粉丝菜谱。含错误未分类项的旧草稿无需手工清空即可恢复后推荐。
- 桌面和手机均无横向溢出，截图人工检查通过。证据为[桌面](../acceptance/ingredient-matching-2026-10-23/desktop.png)、[手机](../acceptance/ingredient-matching-2026-10-23/mobile.png)，最终测试输出目录为`acceptance/ingredient-matching-2026-10-23/browser-verified/`。第一轮页面断言误要求不存在的错误提示元素必须出现，造成2项测试失败；已改为检查错误提示计数为零，原失败证据保留，最终6项通过。
