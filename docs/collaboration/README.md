- 管理员发现分支新提交后，按任务与完整 SHA 审查、验证并串行合入本地 `main`。独立 clone 的提交须先导入当前仓库的任务分支，才能被本地分支检查发现。

- 自动检查需要电脑开机、应用运行、本地仓库可用；没有新提交或等待条件未变时保持安静。

本地审核操作与干净工作区要求见[审核手册](review-runbook.md)的当前执行方式。

用户于 2026-11-05 授权：开发 agent 提交 PR，由当前管理 chat 审核、合入 `main` 并复验。用户另已确认将当前本地项目整理为共同基线，通过初始化 PR 合入远程 `main`。授权包含 Git 提交、推送任务分支、PR 评论和合并；不包含线上部署、真实邮件或新增付费调用。

## 职责与入口

管理 chat 维护任务边界、处理依赖与冲突、独立检查差异和测试、串行合并、复验并登记。开发 agent 负责单个任务的实现、必要检查、PR 和修复反馈，不自行合并或直接推送主分支。各 chat 不共享隐藏记忆，以仓库规则、Issue、PR 和验证证据为准。

- [任务登记](tasks.md)：开发前登记负责人、范围、分支、验收与依赖。
- [审核与合并手册](review-runbook.md)：管理员逐项执行。
- [初始化状态](bootstrap-2026-11-05.md)：旧远程与当前本地基线的差异、证据及剩余设置。
- [PR 模板](../../.github/pull_request_template.md)、[任务模板](../../.github/ISSUE_TEMPLATE/agent-task.yml)。

## 开发约定

1. 从最新远程 `main` 开始，一个任务一个分支：`agent/<agent-name>/<task-id>-<short-name>`；修复可用 `fix/...`，管理用 `chore/...`。
2. 每个 agent 必须使用独立 worktree / clone。不要在管理目录切换分支，也不要共同编辑同一工作目录。新建 worktree 由支持该能力的客户端工具创建；独立 clone 同样可用。各目录依赖、构建产物、端口、测试账号和临时文件分别管理，不复制真实密钥。
3. 在任务登记 / Issue 声明改动范围。`shared/`、Schema、`package*.json`、数据库迁移、`AGENTS.md`、协作规则和检查脚本有交叉时先向管理 chat 报告，依赖 PR 按顺序推进；共享文件不视为永久锁。
4. 不使用 `git add .` 批量混入其他任务，不执行 `reset --hard` / `clean` 丢弃他人工作，不强推 `main`，不擅自回滚已合并任务。
5. PR 先设 Draft；完成必要检查、填写真实证据与回退方式后改为 Ready，并把 PR 链接发给管理 chat。新增提交明确指出变动，旧 SHA 的批准失效。
6. 合并由管理员串行进行。前一个 PR 改变 `main` 后，下一个 PR 更新分支并重新验证；检查运行期间的 `main` 变动也使旧基线失效。
7. 默认 squash 合并，便于每个任务单独回退；初始化 PR 保留既有历史时用 merge commit。冲突先在任务分支处理并重审，不在脏的管理工作区合并。
8. 合并只代表代码进入 `main`。主分支复验通过才将任务记为完成；失败则暂停后续合并，提交修复 PR 或明确 revert PR，复验后恢复。

## 检查与证据

Node.js 24、`npm ci`，默认必查构建、主类型、验收类型与本地单元测试。`npm run pr:check -- --phase pre-merge --base origin/main --head <完整SHA>` 生成绑定 SHA 的本地报告；UI / 健康 / 注册 / RAG 浏览器选择 `--browser core,health,registration,rag` 中相关项。PowerShell 使用 `scripts/run.ps1 pr:check -TaskArguments @(...)` 选择正确 Node 版本。

报告写入忽略的 `.local-data/management/reviews/`。把报告的 SHA、结果、各阶段及缺口摘要写入 PR；不公开原始本地配置与日志中的个人信息。0 表示选定自动检查通过，1 表示失败，2 表示不完整。`preflight` 可在初始化脏工作区执行，但始终不构成可合并通过；正式合并前和合并后要求干净工作区、指定 SHA 和稳定源码。工具不代替代码审查、按变更选择专项或 GitHub 远程状态核对。

规则 / API / 数据 / RAG 按 AGENTS.md 补充相关回归，真实本地 PG 另走已有包装器；未运行不是通过。不新增 GitHub Actions 云端测试或部署工作流，当前只执行本地验证。

## GitHub 强制约束与运行方式

`CODEOWNERS` 只声明责任人，不自动建立分支保护。仓库规则应要求 PR、禁止强推 / 删除 `main`，并在可用时禁止管理员绕过；本地审核结果在 PR 留下对应 SHA 的明确结论。当前未接入自动上传 GitHub required status 的可信执行器，不把本地脚本的退出码当作服务器已强制检查。

若多个 agent 都使用 `pxifer` 身份，同一作者不能正式批准自己的 PR。管理员应提交 COMMENT 类型的审核结论并绑定完整 SHA，不虚构独立审批，也不要设置无法满足的一人批准要求；有独立审核账号后再要求至少一人批准、作废过期批准及解决讨论。GitHub 是否支持这些规则取决于仓库权限和套餐，实际启用状态写入初始化记录。

最初启用的每 15 分钟 GitHub PR 检查已被本页顶部的本地 Git 提交检查取代；没有新增第二个自动任务。

系统逻辑 agent 与 AI agent 可以从同一个已确认基线同时开始，各自使用独立目录和分支；第二个 agent 不需要等第一个开发完成。职责按行为与契约划分，不能仅按 backend/frontend 划分。共同涉及 API、Schema、账户或推荐入口时，在任务中声明接口与依赖。第一个 PR 合并后，第二个 PR 将最新 main 合入任务分支，解决文本与语义冲突后重新审查验证；两个 PR 都必须保留对方已完成的行为。不能保证任意独立改动无冲突自动合并。

可发给其他 agent 的开工指令：

> 先读仓库 AGENTS.md、docs/collaboration/README.md 和任务登记。从最新 origin/main 在独立目录创建 agent/<名称>/<任务编号>-<简述> 分支，只处理分配范围。运行必要本地检查，按模板提交 PR，把链接交给管理 chat；不要直接推送 main、自行合并、部署或进行付费 / 云端测试。
