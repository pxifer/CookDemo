# 拾味项目的用户体验 工程闭环与面试价值审视

核查日期：2026年10月29日。本文提出评审意见和建议完成标准，不变更现有产品决定，不代表已实施下述优化。

当前最值得投入的方向，是把已有的选菜、个人档案和公共证据连成一条可演示、可测量、可维护的完整路径。继续增加病种、菜谱数量或框架，无法单独证明推荐更有用、医学依据更充分或Agent执行更可靠。

项目可以定位为“根据现有食材和个人饮食需求，从真实菜谱中选择一餐，并说明选择依据的助手”。个人级完成态应有明确支持范围，能够长期维护；不需要承担全部疾病组合、诊疗决策或大型平台能力。

## 一 本次判断的依据和范围

本次阅读了当前AGENTS、实际AI选菜与模型调用代码、健康建议来源管理、RAG v2检索、最新专项验收、测试配置及账户清除处理器。浏览器确认了默认域名中间页并进入实际首页，查看了既有桌面/手机验收图；未使用用户Key或调用真实模型。普通推荐交互的本次浏览器尝试未取得可靠的完整结果，因此不把自动化工具的定位与响应读取失败当作产品缺陷。

本次重新运行全仓Node测试：**211项，196通过，14失败，1跳过**，日志见[本次全量测试](../../artifacts/acceptance/project-review-2026-10-29/full-tests.txt)。13项失败在成分核验fixture准备阶段报`COMPOSITION_CORRECTION_MISMATCH`，1项候选目录测试仍期待`candidate_only`。这些失败需按当前产品决定重新分诊，不能直接推导为13种线上功能都坏了，也不能因其历史存在而忽略。

当前能力比前一批面试文档的2026年10月28日初始快照更进一步：

## 二 从网站资深用户角度看

### 首先要让人愿意进入和继续用

**默认域名中间页直接影响信任。** 本次首次进入网站遇到腾讯云测试域名提示，点击确认后才能进入。它不是业务服务器宕机的证据，但会让第一次访问、注册或填写健康资料的人迟疑。面试演示可准备明确说明与离线录像；公开稳定试用则应评估正式域名及所需手续、费用。当前不擅自购买域名或改变零新增账单约定。[CloudBase官方说明](https://docs.cloudbase.net/service/alias)

**需要尽早形成一次完整价值体验。** 主路径应是“录入现有食材 → 搭配 → 看做法 → 换一道或收藏”。健康登录和个人Key连接可以作为增强路径，但普通用户不应先学习Key、模型、三种偏好和多层设置，才能知道网站有什么用。现有普通模式可直接使用，应把这个优势呈现清楚。

**照片入口与实际能力还不一致。** 代码已明确提示图片只预览、识别暂不可用，没有假装已识别；但首页仍将拍照/上传作为重要入口。若图片识别属于既定完整需求，应补“识别候选 → 用户纠正 → 程序确认”的真实闭环，并单独评测。若个人演示版先只完成文字路径，应明确版本范围并降低未完成入口的视觉优先级，不能静默取消既定需求。

### 用户不应承担内部数据与状态的复杂性

**食材名称和导航分类有可复现问题。** 当前`foodGroup`依赖名称正则，本次直接调用得到“肉桂皮→肉禽”“湖南米醋→主食杂粮”；鸡蛋、蟹味菇则分类正确。这是导航分类问题，不是已证实的过敏过滤漏洞。建议以受控食品类别为主、规则为回退，配合别名合并、常见食材排序和搜索，避免让用户在专业部位、加工名和同义项中反复选择。

**长期偏好与本餐决定要容易分辨。** 当前按来源归属、接受/取消和删病撤销已经改善了这个问题。下一步是让用户随时知道“为什么这道菜出现或消失”“这一项只影响本餐还是长期保存”“删掉某个目标后还剩哪个来源在起作用”。优先改善现有解释和操作，不再增加一套重复的偏好系统。

“AI去疾”是已确认过的产品命名，当前不能擅自改名；从新用户理解看，它容易让人联想到治疗。可在后续产品评审中比较“AI食材选择”或“个人饮食避开项”等表达，至少让现有说明明确它是用户接受的选择，而不是疾病疗效或医学确认。

**不同依据应有不同表述。** 至少分清：用户自述、用户接受的偏好、一般模型建议、查到的公共证据，以及未来正式支持范围内的规则结果。不必把技术实现塞进界面，但不能给不同可靠程度的结果相同的“已核验”印象。当前图鉴示例与真正AI选菜已经分开，应继续保留。

### 帮用户完成做饭决策

推荐结果最好回答四个问题：为什么选它、是否需要补买、实际怎么做、不喜欢时怎样替换。人数只影响菜数、固定配方不缩放是当前产品规则，应让初次用户在需要时看懂，避免以为改变人数就自动改变投料。

无结果时给少量可操作选项，如调整菜数、放宽非硬口味或由用户主动开启补买；不能自动放宽过敏忌口，不能把技术失败说成没有菜。继续遵循既有“不展示已有食材缺量/未核实尾注”的决定，不借解释需求恢复已经取消的文案。

补买信息可以形成一份本餐汇总，做法可以优化手机阅读、步骤定位与返回位置。它们都比新增社交、积分、周计划或推荐历史更接近当前核心任务；当前不建议为“完整”堆入这些功能。

**账户生命周期还要闭环。** 已有登录、加密个人设置和来源删除，并不自动等于忘记密码、账号注销及恢复完成。仓库已有`ErasureProcessor`等设计和代码，缺的是对现有CloudBase实际身份与资料路径的端到端证明，不能描述成完全没有删除方案。

### 用户体验需要用任务验证

建议找5至8位目标使用者，使用构造健康资料完成首次配餐、换一道、取消一个接受项、删除目标、处理无结果等任务。记录完成率、到第一份有用结果的时间、误解发生在哪一步、是否知道如何撤销；连续体验几次比询问“页面好看吗”更能发现问题。样本小，只作可用性观察，不包装为市场验证。不会在本轮擅自联系他人或收集健康资料。

## 三 从高级Agent工程师角度看

### 第一优先级是证据到真实菜谱的闭环

当前研究库与线上AI选菜仍是两条链。manifest中`recipeBindings=0`、`clinicalRelease=null`、`embedding=null`。因此扩到更多疾病不是最急的工作；先挑一个明确支持范围，将证据、必要条件、食品身份、真实recipe/variant/method和版本绑定做通。

研究检索与证据解释可以继续开发；正式按疾病执行的规则需要相应审核和发布。可以先用构造规则验证流程，但应标明构造，不能把论文来源或用户接受按钮当成项目规则的专业批准。个人项目若不能取得完整专业审核，应把公开能力限定为饮食偏好与可追溯证据辅助，清楚说明未提供临床适宜性判断。

### 第二优先级是候选覆盖与结论范围

当前选菜器只把最多48道父菜谱交给模型，catalog还受60000字符限制，做法只提供节选。这个设计有合理的成本动机，但有三个必须解决的问题：

1. 好菜是否在进入模型前就被预筛掉。把候选发现质量与模型排序质量分别评价，不能只测模型能否返回catalog内ID。
2. 必要做法或条件是否被截断。关键食材、方法差异与条件应结构化保留，不能从第七步开始丢了关键内容还让模型作完整判断。
3. 局部拒选是否被说成全库无解。当前空choices分支返回`no_results`和`search:'complete'`，契约需区分“此次模型候选处理完成”和“全目录没有可用解”。这属于范围表达风险，不是本次已复现的全库漏推荐事件。

可先在模型包内加入候选数量、总合格目录数量、截断原因、关键字段完整性及检索版本；必要时做一次有界扩候选。用户不必看到调试字段，但服务端与评测要知道结论覆盖了哪里。

### 第三优先级是理由的证据约束

目前ID、长度、重复父菜谱、库存和硬条件有程序复核，这是值得保留的设计。但“ID合法”和“理由可信”是两个问题。做法真实不代表模型关于疾病的解释就有依据。

建议把理由拆成程序可以支持的事实，如复用食材、符合已接受偏好、少补买、来自某证据命题。可执行或公开声明的医学关系必须有相应有效依据；一般模型意见保持其来源身份。未来理由契约带claim类型与evidence ID，服务端核对存在性、版本与适用性，再生成简短说明，而不是仅用禁止词或另一模型投票保证正确。

### Agent自主性应围绕真实失败增加

当前主链路更准确的描述是“确定性工作流中嵌入模型选菜”。它已经有工程价值，但还没有模型自主决定工具和步骤的完整Loop。若目标岗位重Agent，可以补一条受限路径：识别缺信息或缺证据 → 从允许工具中决定补检索或澄清 → 依据结果继续 → 达到预算或条件不足时停止。

只需少量工具，如`retrieveEvidence`、`getRecipeDetails`、`checkMealConstraints`，明确输入输出、只读权限、允许状态及次数上限。先和固定流程对照是否提高任务成功率，不为简历引入自主写库、多Agent投票或复杂框架。架构选择应取决于实际任务，不取决于名称新旧。[Agent与工作流](https://www.anthropic.com/research/building-effective-agents)、[工具设计](https://www.anthropic.com/research/writing-tools-for-agents)

### 上下文管理应先处理预算与信息结构

当前`chatContext`保留最近14条历史加当前问题，并在超过16000字符时按完整轮次删除，这是有界滑窗，不是结构摘要。选菜器也以字符控制catalog。下一步先按所选模型校准token预算，拆出权威档案、当前目标、近期对话、证据和候选字段，再试结构摘要。

健康硬限制、来源归属、最新更正、未完成任务、已完成操作和确认状态不能只存在摘要里。摘要仍留在会话内存，不默认长期保存完整聊天；模型切换和来源删除后重建权威状态。评测看整段会话，包括摘要调用的成本、任务成功和约束保留。[上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

### 可靠性要沿用现有优点并验证真实边界

当前已有共享PG认领、前后账户/档案复查、晚到结果处理、取消、无自动重发、15分钟加密游标，以及分页不追加模型调用。这些可以成为项目亮点。

后续重点是实际PG多连接和云函数实例间验证。共享单次认领与整条任务状态一致性不是同一个问题：`backend/src/app.ts`的`latest`仍是进程内Map，需要定义跨实例、不同标签页和不同本餐实例的版本语义，再决定哪些状态应进入数据库。不能据此断言当前一定会串资料，也不能用单连接PGlite宣布云端并发已验证。

内部应能看见一次操作的阶段、配置版本、候选规模、token、耗时、错误和是否已认领，便于定位慢与贵。目前调用助手返回usage，但选菜路径未把`response.invocation`纳入可复用结果，通用认领记录也不足以形成完整成本评测。建议增加最小化的内部观测契约，保持UI不显示调试调用信息、日志不保存健康正文和Key的既有决定。

## 四 怎样定义个人项目的完结态

完成不意味着所有愿望都实现，而是选定支持范围内的任务能稳定交付，范围外能正确退出。范围调整是后续产品选择，不在本次评审中自动生效。

| 维度 | 建议的个人v1完成标准 |
| --- | --- |
| 核心用户路径 | 无Key能完整体验普通推荐；配置后AI可根据真实候选选菜；换菜、做法、收藏和错误恢复可用 |
| 输入 | 文字与手动入口可靠；真实识别若纳入本版，则有候选确认和纠错闭环，不能以预览冒充识别 |
| 健康范围 | 声明支持的疾病/目标、条件与不支持组合；研究与正式执行分开，未完成审核不冒充临床推荐 |
| 数据闭环 | 选定范围内的证据、事实、规则、真实变体和做法能定位；更新与撤回不会复活失效结果 |
| AI行为 | 不编造目录ID、不绕过硬限制；补检索、取消、失败和预算耗尽有明确终态 |
| 长会话 | 不丢关键限制、来源与最新更正；压缩收益和总成本可测 |
| 账户与运维 | 密钥配置/清空、忘记密码、注销和资料删除有明确可用性；至少完成一次真实备份恢复演练 |
| 测试 | 稳定范围内无未分诊失败；集成未测项明确；关键AI浏览器回归进入统一验收入口 |
| 质量证据 | 有独立检索/任务集、获授权的真实模型小样本、延迟费用和失败分类，不能全靠mock |
| 展示 | 网站入口可靠，一段短演示、一张当前架构图、一份可复现报告和两三个失败复盘 |

无需作为个人v1前提：支持全部疾病组合、上千菜谱、专用图数据库、Redis/MQ、微服务、自动网页爬虫或多Agent平台。模型和服务增加之前都应有收益证据。

## 五 生产和维护流程怎样改进

### 内容与知识生产

将流程固定为“来源登记 → 解析与定位 → 候选实体/关系 → 校验与核对 → 条件和冲突 → 真实菜谱绑定 → 评测 → 冻结版本 → 发布或保留研究 → 更新/撤回”。

AI可协助找材料、抽取和提出冲突，但来源、原文定位、单位、条件及执行资格需要核验。每次只扩一个可验证缺口，不以病种数量作为主要产出。事实包、切片、词典、编码协议与规则版本形成manifest，可重复构建；维护者能说明改了哪条依据、影响哪些规则和菜谱。

初期可用JSON/CSV加受控脚本维护，不必先建完整后台。来源许可和普通菜谱发布继续遵循现有决定，不在本次新增旧审批门槛。

### 软件开发与发布

建议一项需求交付一条纵向路径：用户行为与例子 → 最小接口/状态契约 → UI和后端一起实现 → 相关验证 → 冻结候选版本 → 发布前集成 → 灰度和回退。避免分别生成一套前端、一套API和一套RAG后再集中拼接。

仓库里有多个专项测试配置和按发布版本命名的脚本，本次未见`.github`下版本化CI工作流。默认`check`调用的浏览器配置明确忽略健康聊天专项，不能把默认check通过当成所有核心AI路径已验收。

建议建立一个统一的验收编排入口，按变更路径选择领域测试、健康专项、数据完整性与必要集成，输出一张能力表。把可复用部署参数和检查提炼出来，历史脚本、迁移和验收保留；不要为清爽删除恢复依据。采用现有资源可运行的本地/CI检查，不先新增收费服务。

每份结果至少绑定源码指纹或commit、依赖锁hash、内容/知识manifest、模型配置、数据集版本、命令、结果与未测项。模型API兼容不代表版本行为永远不变，应保留固定契约样本作升级回归。

## 六 测试与评测怎样改进

### 先恢复测试信号的可信度

本次14项失败应先分三类：现有行为确实错误、产品决定已替代旧断言、fixture或构建方式过期。对每项写清当前依据和修复方式；例如成分fixture创建失败时，后续权限和撤回断言根本没执行，不能当作这些能力已通过。

修改过时fixture时保留它原本验证的行为；修改断言时说明是哪条产品决定改变预期。允许有明确原因和重新检查条件的暂时隔离，但不能长期把全部失败藏进ignore或skip，也不能把旧全量结果与新专项结果混成“全绿”。

### 建立分层质量矩阵

| 层 | 主要验证 | 建议方法 |
| --- | --- | --- |
| 数据 | 原文定位、单位、hash、关系端点、条件、真实菜谱绑定 | 结构校验与人工抽查分开 |
| 业务规则 | 过敏忌口、补买、未知量、整餐累计、换菜与收藏复查 | 固定案例和有意义的不变量测试 |
| 检索 | 相关命题、必要限定、歧义、错字、形态、冲突、零证据 | 分组冻结集和逐题候选trace |
| 模型 | 合法结构、真实ID、理由支持、拒选、幻觉、截断 | mock契约加真实模型样本 |
| Agent | 路由、工具参数、无效循环、预算、取消、完成状态 | 任务结果和执行轨迹共同评价 |
| 前端 | 首次配餐、接受/取消、删来源、换菜、手机做法 | 语义定位和用户可见结果断言 |
| 集成运维 | 多实例认领、晚到结果、撤回、密钥变更、恢复 | 真实PG/云环境故障注入 |
| 可用性 | 是否得到想做的一餐、能否解释和撤销 | 小样本任务观察和自愿反馈 |

用浏览器测试验证用户看到和能操作的行为，减少依赖固定卡片位置、按钮细微措辞和偶然排序；用可重试语义断言处理异步，不靠固定sleep。失败trace仅用于构造账号/公共数据，不能默认采集真实健康正文。[Playwright实践](https://playwright.dev/docs/best-practices)、[断言说明](https://playwright.dev/docs/test-assertions)

### 检索评测需要真正的未见问题

200题是可执行的起点，不是神奇门槛。按问题簇、来源和风险分组，开发集用于改进，冻结集不用于调参；以稳定证据命题/span标注，切块版本改变后仍能比较。模型生成题只作为候选，关键题须独立核对。缺独立标注时继续称编辑回归。

除了Recall@k和nDCG，还看必要限定全部覆盖、条件错配、无答案误接收、过度拒绝、引用支持和实际菜谱资格。当前50/50及困难题10/10是有价值的回归证据，但不等于独立泛化；当前A1的暖态内存速度观察也不能包装成云端QPS或稳定提升百分比。

向量实验比较当前A1、A1加dense/RRF、再加rerank；如无收益就保留简单方案。全流程优化需要把候选召回和模型选择分开，不让好的模型掩盖差的候选池。

### 真实模型评测要补上

先用公共食材和明确构造档案准备少量完整任务，在费用和有效测试Key有相应授权时实际运行；记录任务成功、无效输出、理由支持、取消/超时、P50/P95和所有调用的token。对部分任务重复运行观察波动。当前本次没有有效Key推理调用，也不借用用户保存的Key。

mock回答“选c3”可以证明程序采纳c3，不能证明模型能读懂做法并选对c3。LLM judge可辅助筛查，但不能自己出题、作答和打分后独自证明成功；关键事实和执行结果仍需要外部依据。[Agent评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### 最值得补的故障组合

同ID重复与同ID异输入、跨实例晚到、取消后上游仍返回、生成中删目标或换Key、证据撤回、目录更新、游标过期与篡改、长期对话更正、候选截断、未知成分/形态、模型合法JSON但理由不受支持。每个用例都验证最终状态和副作用，不能只看模型是否说“已取消”。

## 七 怎样与AI交互才能更快生成可靠项目

有效速度应计算“从需求到可验收交付”的总时间，包含返工和定位。让AI一次写更多代码，不一定能缩短这个时间。

### 固定少量权威上下文

维护一个短项目入口：当前产品决定、真实能力表、模块地图、运行和验收命令、当前失败清单、资料/费用边界。详细证据保留链接，不把所有旧文档每轮塞进上下文。新需求先检查已实现部分，明确由哪条后续决定覆盖旧规则。

每个任务另给一张简短任务卡：用户行为、当前问题和复现、完成例子、影响范围、验收方法。人负责目标与取舍，AI负责读代码、提出实现、完成修改和验证；不要每一步都停下来确认，也不要让AI替用户决定新增成本与资料保留。

### 一轮任务完成一个可审查结果

推荐同一任务里顺序完成“核实现状 → 明确最小契约与关键失败例 → 实现 → 验证与评审 → 交付”。不用先花很长时间写穷尽设计，也不把大重构、界面改版和换数据库同时塞进一次交付。

出现失败时提供预期、实际、最小输入、错误和对应版本，让AI定位哪一层出了问题，再修复。不要用“还是不行，再优化一下”触发无边界改动。用户体验修改用截图和目标操作验收；模型质量修改用冻结题集与失败分类验收。

### 可以直接复用的任务提示

```text
目标：让用户看懂本次AI选菜为什么使用某条依据，
并在依据撤回后停止展示受影响结论。

先核对AGENTS、最新代码与验收，区分已完成和仍缺部分。
本任务只完成一条证据到一个真实菜谱变体的纵向路径。
普通推荐规则、既有账户资料保留和个人Key调用约定沿用当前决定。

完成标准：
1. 有效证据能定位到原文、条件和真实variant/method。
2. 缺证据、条件未知、撤回和版本变化分别有明确结果。
3. 模型不能编造证据ID或改变用户硬限制。

请完成必要的契约、实现、相关测试和页面核验后交付。
已有失败先分诊；如修改断言，说明当前需求依据并保留原验证目的。
不新增收费资源或调用真实个人Key；外部依赖缺失时完成可独立验证部分。
最后提供改动、验证、剩余缺口和一条可复现命令。
```

不必为可逆局部选择反复问用户。涉及范围实质变化、费用、真实资料或不可逆发布时，先把可独立完成的结果做成可审查状态，再处理对应边界。

## 八 从面试角度还需要探索什么

### 深入方向一 可解释检索与证据治理

你需要能手写和解释实体匹配、词法通道、RRF去重、条件过滤、必需证据与撤回，而不只是调用框架。挑一个真实失败，例如不饱和/饱和脂肪酸短词碰撞或鲜干形态混用，展示输入、旧候选、改动、回归和独立集结果。

A1已经提供可讲的具体改进。下一步是补独立测量与真实菜谱绑定，再决定向量是否值得加入。面试亮点可以是“拒绝了无收益组件并说明依据”，无需强行选一个向量库。

### 深入方向二 受约束的Agent执行

补一条确有动态分支的小Loop，展示工具注册、参数校验、权限、观察、停止条件与预算。对照固定流程，说明它在哪类问题减少漏证据、在哪类问题只增加成本。精读一个开源runtime的固定commit，沿消息、模型、工具、取消和压缩画调用链；不必同时泛读多个框架。

如果Loop没有业务收益，就把项目如实称为AI工作流，并另做小型对照实验；这比包装成全自主Agent更经得住追问。

### 深入方向三 并发 状态与可恢复性

能解释PG原子认领、CAS、请求版本、跨设备来源删除、晚到结果和外部执行未知之间的区别。完成一次真实多连接重复请求、生成中删目标、证据撤回和恢复演练，保留脱敏时序图与状态结果。

按来源保存建议、删目标不复活旧接受记录、15分钟绑定游标且翻页不消费，已经是很好的个人项目工程材料。需要亲自理解代码与失败窗口，而不是只背验收文字。

### 深入方向四 上下文和成本优化

实现权威状态加会话内摘要，设计最新更正、早期限制、删除来源、长工具结果和切模型的多轮任务。统计完整会话所有输入输出、摘要、失败调用和缓存口径，报告质量与总费用。没有实测之前不写“节省50%”。

同时理解应用字符数、tokenizer、供应商usage、上下文窗口与KV cache不是一回事；能解释API与本地部署在资源、资料、费用和维护上的取舍。

### 深入方向五 用户与产品反馈

做少量真实任务观察，记录为什么用户不要这道菜、是否看懂少选/避开、是否能找到撤销和是否愿意再次使用。按自愿、最小化原则处理资料，不为面试擅自启用推荐历史。没有用户数据时如实展示可用性观察方法，不编造留存、转化或QPS。

### 把成果做成面试官能检验的材料

至少准备：一个可靠演示入口与2至3分钟备用录像、一张当前架构图、一套可复现的独立任务集与报告、一个真实调用的脱敏trace、两三个失败复盘，以及对应代码。每个亮点都能回答“为什么选、实现在哪里、怎么测、还缺什么”。

推荐最终讲述重点：

- 真实目录与硬约束保护下的模型选菜和有据解释。
- 按疾病/目标归属、可撤销且跨设备不复活的个人偏好。
- 带条件、版本、冲突与撤回的检索证据链。
- 经任务对照验证的上下文与调用成本优化。

前三项已有较多实现基础，第四项仍待完成。不要把它们写成四项已全部上线。

## 九 建议推进顺序

| 顺序 | 交付 | 结束条件 |
| --- | --- | --- |
| 1 | 更新当前能力表 分诊14项失败 统一验收入口 | 能明确说哪些通过、哪些失效、哪些未测 |
| 2 | 完整用户主路径与小样本可用性观察 | 首次配餐、换菜、撤销和无结果可理解可操作 |
| 3 | 一个范围的证据到真实菜谱闭环 | 引用、条件、绑定、撤回能在同一演示中完成 |
| 4 | 独立评测与获授权的真实模型小样本 | 有可信分母、失败分类、延迟和费用 |
| 5 | 候选覆盖、Embedding与重排对照 | 能基于项目结果选择保留或增加组件 |
| 6 | 小型受限Agent与上下文优化 | 任务收益、约束保留和总成本有可复现对照 |
| 7 | 账户运维与展示收尾 | 真实删除/恢复边界、发布版本和演示材料齐全 |

这些是依赖顺序，不是“做完七步之前不能发布任何改进”。可独立验证的产品修复可以随时交付；不把专业审核缺失当作停止所有研发的理由，也不让持续扩范围取代已有承诺的收尾。
