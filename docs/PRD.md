## 2. 项目背景、目标用户与产品目标

### 2.1 项目背景

用户做饭前通常已经拥有部分食材，但需要同时考虑吃什么、能否凑齐一餐、现有调味料、口味、份量和用餐限制。拾味帮助用户将现有食材整理成可确认的信息，获得可执行的单餐菜谱方案。

现有Demo已验证主要界面路径，并发现6项有复现证据的Bug；正式产品还需建设真实识别、可追溯菜谱内容、单菜口味变体、真实账户及受验证条件限制的健康功能。

### 2.2 目标用户与场景

- 主要用户：独居用户及1–4人家庭的日常家常做饭人群。
- 主要场景：拍下或写下手头食材，核对后安排当前一餐；希望省事、减少额外采购，并尊重已确认的用餐限制。
- 次要场景：为多人放大份量；主动合并他人附加限制；查看已收藏菜谱及其口味。
- 终端：手机优先，兼容桌面浏览器。

1–4人是重点服务场景；1–12人是已确认的可输入范围，二者不是同一个限制。

### 2.3 产品目标

1. 从食材输入到菜谱做法形成可理解、可修改、可恢复的完整流程。
2. 让用户清楚区分“有这个食材”“数量够用”“尚未核实”“需要补买”。
3. 让已确认限制与推荐、换菜、口味变体及收藏复查保持一致。
4. 对识别与数据不确定性明确反馈，不以模拟结果或虚构依据冒充真实能力。

### 2.4 阶段边界

本PRD描述正式首版需求；当前任务仅编写文档。具体技术栈、数据库、接口、模型、RAG、LightRAG、Agent及多模型编排均留给技术设计阶段，不在本文预选。

## 4. 核心用户流程

### 4.1 普通推荐主路径

| 步骤 | 用户操作 | 系统输出与条件 |
| --- | --- | --- |
| 1. 进入工作台 | 开始新一餐或继续当前草稿 | 新餐加载默认；继续则恢复本机草稿；显示当前人数及限制作用范围 |
| 2. 输入 | 拍照、上传图片、输入文字，或主动试用明确标注的示例 | 提取候选信息；真实输入与演示来源清楚区分 |
| 3. 核对 | 编辑名称、可选用量，确认、删除或补录项目 | 确认食材进入可用清单；疑似项保留且不参与；未知过敏项要求处理 |
| 4. 设置 | 选择人数、饮食偏好、全局口味、库存策略、附加限制及推荐模式 | 展示本餐生效条件；数量选填；补买由用户主动接受 |
| 5. 推荐 | 确认并生成 | 执行已确认限制、库存、份量及复用规则；条件不足时减少菜数或解释无结果 |
| 6. 调整与查看 | 换一道、整套重推、翻页、改口味、打开详情 | 保持相关输入；更新对应结果，不以按钮外观变化代替真实结果变化 |
| 7. 收藏或保存默认 | 收藏当前菜谱口味，或主动保存默认设置 | 收藏内容按FR-09处理；默认资料按FR-12处理，不能相互隐式替代 |

收藏前是否必须登录尚未确定，普通推荐流程不因此新增登录步骤。健康模式登录要求已确定。

### 4.2 健康模式分支

1. 用户主动开启健康模式；普通模式下提取到疾病名称不会自动开启。
2. 未登录时进入真实登录流程，完成后返回原用餐流程并保留本餐输入。
3. 通过列表或自然表达录入名称，识别别名后核对标准名称；已识别不等于已支持。
4. 名称确认后检查是否在已验证支持范围，以及当前条件能否同时满足。
5. 支持且可满足时，展示相应菜谱、具有可核对来源的营养信息及有依据的说明。
6. 不支持或不能满足时，停止健康推荐，提供修改信息或主动切回普通模式的出口。
7. 切回普通模式保留食材、人数、口味和库存等本餐设置；过敏与明确忌口仍生效。

### 4.3 恢复与重新开始

- 刷新：恢复文字草稿和确认状态；原始图片不长期保存。
- 进入演示：使用独立演示状态，不把演示值写成个人资料或真实本餐草稿。
- 退出或在演示中刷新：退出演示，恢复进入前草稿。
- 开始新一餐：清空本餐，恢复已保存默认，保留资料与收藏。
- 清空Demo数据：明确确认后清除相应演示数据；真实账户云端删除范围见A-06，不由该操作名自动推定。

## 5. 功能需求

本章功能均为**v1新增或完善**；Demo对应状态见第3章。规则编号见第6章，验收编号见第10章。

### FR-01 图片与拍照输入

- 提供拍照与上传入口，展示本次图片预览和真实识别结果。
- 结果可进入统一确认、编辑和合并流程；无法识别时保留原输入并允许补录或重试。
- 不使用固定五项示例伪装真实识别。演示识别必须明确标注来源并遵守场景隔离。
- 原图不长期保存；真实处理是否涉及传输、短期暂存及相关说明待后续确定，不能直接沿用Demo“图片不会上传”的描述。
- 正式图片格式、大小上限和处理时限未确定，不将Demo的12MB限制直接写成正式上限。

### FR-02 连续文字与混合信息提取

- 支持不依赖逗号、顿号的连续中文输入，识别多个名称及对应数量、单位。
- 同一段话可提取食材、人数、过敏、明确忌口与疾病，按类型展示供核对。
- 支持自然表达与标准清单录入限制，二者应进入一致的确认与应用规则。
- 保留原文用于用户核对；不把后续多个食材的文字塞进第一项用量。
- 提及某食材不等于对它过敏；否定或允许表达不自动移除已保存限制。

### FR-03 信息确认、编辑与追加合并

- 支持改名、修改可选用量、删除、新增及人工纠错。
- 新图片或新段食材输入默认追加到现有清单，同名项合并。
- 同名数量冲突保留供核对，不直接相加、覆盖或悄悄丢失。
- 不确定食材保留为待处理且不参与推荐；用户可以确认其他食材后继续。
- “食材尚有疑似项”不与“过敏尚未确认”共用同一继续规则，见BR-03。

### FR-04 个人限制、附加限制与冲突确认

- 分开记录过敏、明确忌口、口味偏好；前两类属于不自动放宽的限制。
- 对宽泛名称保留类别与已确认范围；不能仅显示原文就声称已经排除。
- 默认应用本人限制；用户主动选择后合并一份已保存的他人附加限制清单。
- 新文本与已保存限制冲突时保留原限制，逐项确认变更。
- 在推荐摘要中显示人数和本人／合并附加限制的作用范围，不因人数变大就宣称覆盖了所有人的个人资料。

### FR-05 食材用量、单位与数量状态

- 用量始终选填；提供食材常用单位并保留其他输入、约量和空值。
- 明确区分数量足够、已知不足、数量未知和单位无法比较。
- 已知数量可以比较时参与单菜及整套餐累计核对；无法比较时不伪造确定结果。
- 接受补买后，对可核对食材展示整套累计缺量；数量未知项只标需核对，不计算假差额。

### FR-06 调味料清单与库存策略

- 提供默认清单及本餐修改入口，支持勾选有无；保存默认须由用户主动操作。
- 未保存检查偏好时默认不检查库存，仍展示菜谱调味料。
- 开启检查后处理必需缺项及明确可省项；接受补买后展示缺调味料。
- 不检查库存不等于不检查配料中的过敏原或明确忌口。

### FR-07 套餐推荐与多菜候选

- 一键套餐默认三道，支持指定荤、素、汤数量；总数1–6道。
- 多菜候选每页六张，家常菜优先，特色和创意菜随后。
- 每道菜卡展示名称、食材信息、相关数量或缺项状态、估算热量及详情入口。
- 支持单道替换、整套重推、翻页；有其他可行候选时实际更新结果，无候选时说明原因。
- 食材不足时减少菜数并提示原因，不为凑数自动接受补买或放宽限制。
- 正式自动三道菜的具体荤素汤配比及选择顺序仍待确认，不将Demo中的组合轮换算法作为既定业务规则。

### FR-08 全局及单菜口味变体

- 全局口味为默认，菜卡展示该菜可用的口味选择；选择后提供对应做法。
- 单菜手动选择优先于后续全局口味修改；清楚标出各菜当前口味。
- 变体主料不变，允许调整辅料、调味料、用量与步骤。
- 同步核对限制、库存、补买条件和营养信息，不符合已确认限制的变体不可选。
- 正式口味及各菜可用变体范围见A-01；Demo口味标签本身不是已验证的变体内容。

### FR-09 菜谱详情与收藏

- 详情包含菜谱食材、建议用量、调味料和步骤；普通模式重点展示热量，健康模式展开详细营养及经验证的相关说明。
- 展示每人份／当前人数的口径，避免把单人份估算误标为整餐总摄入。
- 收藏保存菜谱及选定口味；再次打开按当前人数计算用量，并复查当前限制。
- 收藏身份门槛见A-05；不能据当前Demo需要演示登录就推定正式游客必须登录才能收藏。

### FR-10 真实账户与跨设备保存

- 普通推荐允许游客使用，健康模式需要真实账户登录。
- 登录后同步长期资料和收藏；本餐草稿首版保留在当前设备。
- 登录及返回原流程不丢失本餐输入与已确认设置。
- 不以本地演示登录表示真实注册或跨设备同步已经完成。
- 登录方式及同步实现留给技术设计；游客默认资料和登录合并的具体口径见A-07。

### FR-11 健康模式、营养与依据

- 支持疾病列表、自然表达、别名归一及标准名称确认；不从用户表达推断确诊。
- 高血压、糖尿病、痛风仅优先评估，通过依据审核才列入支持名单。
- 未支持项目、无法确认的依据或无法同时满足的约束，不能输出确定性适宜结论。
- 健康说明应能对应可靠来源，并说明适用范围和不确定性；缺数据或依据时不编造数值、引用或结论。
- 营养按菜谱建议用量估算；普通模式重点展示热量，健康模式展开营养。
- 饮食目标仅为均衡、偏清淡、偏少油等偏好，不承诺个人减脂或增肌效果。

### FR-12 默认资料、本餐草稿及演示隔离

2026-10-24用户明确修订（D16-03）：登录后自动恢复并保存个人口味、本人过敏/忌口和调料设置；游客仅本机使用，保存到账户需要登录。入口称“个人设置”，取消手动“常用偏好”保存及常规登录合并选择；人数和食材等本餐信息不同步。此修订覆盖下方主动保存默认及A-07的相应交互，硬限制冲突、账号隔离和草稿保留规则不变。来源见[决策日志D16-03](technical/decision-log.md)。

- 工作台修改默认仅本餐生效；通过个人设置或“保存为默认”主动更新长期资料。
- 自动保留文字食材、可选用量、人数及本餐设置，刷新恢复确认状态。
- 演示场景独立运行；退出或刷新恢复进入前草稿，不污染长期资料。
- 提供“开始新一餐”和“清空Demo数据”两个入口，分别说明影响范围。
- 具体保留表见第7章；不借新增真实账户能力自行扩大清空Demo的删除范围。

## 7. 资料、草稿与演示数据保留规则

### 7.1 三层数据

| 数据层 | 内容及范围 | 更新与恢复 |
| --- | --- | --- |
| 长期个人资料 | 用户主动保存的本人过敏／忌口、附加限制、饮食偏好、默认口味、默认调料及经确认保存的疾病信息等 | 个人设置或保存默认时更新；账户同步能力按FR-10；游客保存与合并口径见A-07 |

疾病弹层中的未提交文字应在点击标签时保留，见B05；这不自动形成“未提交疾病文本必须跨刷新保存”的要求，后者仍待明确。

### B01 · P1 · 未确认的过敏表达被显示为已生效

**复现范围：** 桌面与手机模拟。原记录检查组：`ALLERGY_KNOWN_AND_UNKNOWN_ALIAS`。

**原复现步骤：**

1. 重置；个人设置保存本人过敏“海产品”。
2. 添加西红柿、鸡蛋、土豆、虾200g、鱼400g。

**修复预期与验收条件：**

- 若已能明确支持范围，展示类别及范围，用户确认后正确执行。
- 若无法识别或范围不明确，保持待确认并暂停推荐，不能显示已应用。
- 已确认限制在推荐、换菜和变体中一致执行；不得仅通过修改标签掩盖未执行的限制。
- 不据该Bug推断所有自然表达都失效，不承诺未经验证的全量过敏覆盖。

**证据：** [桌面截图](../review-assets/05-allergy-unrecognized-alias.png)、[手机截图](../review-assets/m-05-allergy-unrecognized-alias.png)、[桌面记录](../review-assets/playwright-evidence.json)、[手机记录](../review-assets/mobile-playwright-evidence.json)。

### B02 · P1 · 演示场景污染已保存的过敏资料

**复现范围：** 桌面与手机模拟。检查组：`SCENARIO_PERSISTENCE_ALLERGY_LOSS`。

**原复现步骤：**

1. 重置；个人设置保存本人“虾”。
2. 点击底部“日常一餐”，展开限制查看字段。
3. 点击“清淡”。
4. 刷新，再查看本人过敏。

**实际结果：** 场景载入后字段为空，提示却称“不改变已保存的个人设置”；切口味后刷新，原“虾”仍为空。

**修复预期与验收条件：**

- 原已保存“虾”不因场景、切口味、切库存策略及刷新被改写。
- 演示临时限制不进入个人资料持久保存。
- 正式草稿能力新增后，进入场景前的本餐草稿在退出／刷新时恢复，见AC-25；不能声称原Demo本来就有该草稿能力。
- 所有演示场景作为后续回归范围，不把原单条复现外推为所有字段都已丢失。

**证据：** [刷新后截图](../review-assets/06-saved-allergy-lost.png)、[桌面记录](../review-assets/playwright-evidence.json)、[手机记录](../review-assets/mobile-playwright-evidence.json)。

### B03 · P1 · 单位不兼容时静默放行库存数量判断

**复现范围：** 桌面与手机模拟。检查组：`UNIT_COMPATIBILITY_AND_MISSING_HINT`。

**原复现步骤：**

1. 重置，输入“西红柿1g、鸡蛋1g”。
2. 设置12人，不接受补买。
3. 生成套餐。

**实际结果：** 返回番茄炒蛋、番茄蛋花汤，标12人份及“手边就有”；没有单位无法核对提示。页面未明确声称“足量认证”，但未暴露数量核对失效。

**修复预期与验收条件：**

- 食材及受影响结果明确标明单位无法比较、数量未核实。
- 按本次已确认规则，允许推荐，不强迫补数量或增加继续确认步骤。
- 不能把这些库存标为已核实足量，也不能未经验证把g换成个。
- “返回菜谱”本身不是修复后失败条件；缺少真实状态和误导足量才是该Bug的关键。

**证据：** [截图](../review-assets/04-unit-mismatch.png)、[桌面记录](../review-assets/playwright-evidence.json)、[手机记录](../review-assets/mobile-playwright-evidence.json)。

### B04 · P2 · 就餐人数接受小数且没有校验反馈

**复现范围：** 桌面与手机模拟。检查组：`SERVINGS_INTEGER_AND_FRACTIONAL`。

**原复现步骤：** 添加正常示例食材；直接输入就餐人数1.5；移开焦点并推荐。

**实际结果：** 摘要及结果显示“1.5人份”，没有校验提示。

**修复预期与验收条件：**

- 人数以1–12整数为有效范围，1.5等非法值不得直接形成对应人数方案。
- 对不合法输入提供纠错反馈，输入、加减按钮和生成行为一致。

### B05 · P2 · 选择疾病标签清空草稿并丢失焦点

**复现范围：** 桌面与手机模拟。检查组：`HEALTH_NATURAL_TEXT_CONFIRMATION_AND_DRAFT`。

**原复现步骤：** 演示登录进入疾病设置；先确认高血压；在文本框输入“偏头痛”但不识别；点击列表“糖尿病”。

**实际结果：** 文本框变空，焦点落到BODY。

**修复预期与验收条件：**

- 点击疾病标签不丢失未提交文字，保留合理焦点。
- 已选项目与正在输入的草稿清楚区分，不能因草稿保留就自动应用未确认疾病。
- 不把该样例外推为所有弹层均存在草稿丢失；跨刷新保存未提交疾病文本仍待明确。

**证据：** [桌面记录](../review-assets/playwright-evidence.json)、[手机记录](../review-assets/mobile-playwright-evidence.json)。

### B06 · P2 · 接受补买后不显示已有食材的数量缺口

**复现范围：** 桌面精准菜卡样例。检查组：`EXACT_QUANTITY_PURCHASE_GAP`。手机只覆盖了相邻的数量不足路径，不能标成该精准样例双端已验证。

**原复现步骤：**

1. 重置，输入鸡肉1g、香菇1g，设置12人。
2. 切换多菜候选并推荐，接受补买。
3. 打开“香菇滑鸡”。

**实际结果：** 卡片显示“手边就有 · 鸡肉、香菇”；详情需鸡肉1440g、香菇720g，没有数量差额，仅有通用用量说明。

**修复预期与验收条件：**

- 沿用该演示用量样例，显示鸡肉还缺1439g、香菇还缺719g，不继续以无短缺提示的“手边就有”呈现。
- 正式套餐按整套累计后核对缺量；未知量不得计算假差额。
- 原Bug是确定短缺信息遗漏；精确差额与整套汇总是本轮已确认的完善要求，追踪到FR-05、AC-10，不扩充现有Bug数量。

**证据：** [精准截图](../review-assets/15-exact-quantity-gap.png)、[补充记录](../review-assets/follow-up-evidence.json)。
