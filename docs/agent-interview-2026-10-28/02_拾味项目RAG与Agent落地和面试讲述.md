# 拾味项目RAG与Agent落地和面试讲述

从现有代码到可验证的健康知识与菜谱推荐

现状核查日期 2026年10月28日

拾味的目标是帮助家庭根据现有食材、库存、口味和限制选择真实菜谱，并逐步加入有证据的定性健康食材指导。项目最值得深入的部分，是让公共证据、个人意图和确定性推荐共同工作，并让每条结论可以追溯、撤回和验证。

推荐路线是保留现有 TypeScript 模块化单体与 PostgreSQL，先补齐知识与真实菜谱绑定、独立评测和查询契约，再比较向量、重排与受限 Agent。下一阶段的项目上限取决于证据质量、规则条件和评测闭环，不能用增加模型或框架数量代替这些工作。

本文件分为实际现状、从零建设步骤、关键问题与追问、项目讲述四部分。代码路径相对 `CookDemo/`。当前状态来自代码和本地记录；已部署描述依据既有验收，本次没有再次访问生产环境或实际消费模型额度。

### 本次新增的只读复核

复核直接调用现有 `validateKnowledgeBundle` 与 `searchKnowledge`，读取当前知识包和已有20题；没有改检索代码，也没有生成新模型答案。对每题检查所有 `expectedFactIds` 是否在前k条中。

| 口径 | 结果 | 含义与限制 |
| --- | --- | --- |
| 全部预期事实在前1条 | 18/20 | 有一道题需要两条事实 本来就不可能全部占首位 |
| 全部预期事实在前5条 | 20/20 | 是当前词面较直接编辑题的完整预期事实覆盖 |
| 全部预期事实在前10及20条 | 均20/20 | 不代表所有相关证据都已被人工穷尽标注 |
| 未提供临床条件的查询 | 保留needs_confirmation等状态 | 没有推断成人 分型或肾功能正常 |
| 完全未知词构造输入 | insufficient_evidence 且不允许执行 | 只说明此构造样例的回退行为 |

这不是证据级 Recall、独立泛化测试、SQL吞吐、线上模型质量或医疗安全率。脚本为 [audit-baseline.ts](support/audit-baseline.ts)，结果为 [baseline-audit.json](support/baseline-audit.json)。面试时最有价值的不是把20/20夸大，而是能解释这个结果证明什么、尚未证明什么。

## 二 从用户问题画出当前链路和目标链路

### 当前链路

普通请求走“输入解析 → 过敏忌口等硬限制 → 真实目录资格和库存检查 → 家常及少补买排序 → 整套餐复核 → 返回”。健康聊天走“认证与CSRF → 读取个人Key和已存资料 → 数据库共享单次认领 → 固定模型调用 → 完整终态和JSON业务校验 → 食材建议 → 程序匹配真实目录 → 用户接受偏好或排除 → 用户另行决定是否筛选本餐”。

目前聊天标记为 `general_model`，不声称查询了已核验RAG。公共研究库是另外一条本地链路，返回证据、条件与冲突，明确不授予线上疾病推荐资格。

### 目标链路

```text
用户明确意图和本餐条件
  → 认证 授权 输入版本
  → 解析疾病 食材 工艺实体及歧义
  → 读取已确认限制和适用的正式规则
  → 规则必需证据按ID取回
  → 关键词与可选向量发现补充证据
  → 融合 重排 去重 回取条件与例外
  → 检查适用性 冲突 撤回与证据覆盖
  → 程序生成定性食材判断
  → 固定目录与变体做完整资格检查
  → 模型按证据整理解释
  → 校验引用 版本 用户提案与本餐状态
  → 展示结果 用户决定是否接受持久偏好和应用本餐
```

模型负责理解和表达，确定性程序负责约束与状态，检索负责发现证据，发布机制决定哪些规则可以执行。这些角色共同完成任务，但不互相替代。适合的架构是外层 Workflow 加内部受限检索Agent。[Agent与Workflow的区分](https://www.anthropic.com/research/building-effective-agents)

## 三 从零建设的十二步及验收产物

### 第一步 定义最小业务闭环

先明确“回答食材选择原因”与“正式按疾病筛选菜谱”是两个交付层级。第一阶段可以展示研究检索和覆盖不足；正式执行则要有适用范围、审核规则和菜谱绑定。普通推荐始终沿用现有硬限制，不因健康知识未完成就阻断无关普通功能。

首个闭环可以限定一个已明确的疾病主题、一组可定位证据、少量真实食材和做法，以三个输出验收：正确引用、条件未知时返回明确状态、与实际变体一致。库里已经有三主题，不需要退回让用户重新选择首个疾病或重复建同一批资料。

**产物**：范围说明、状态枚举、10至20条验收样例、当前与目标能力表。病例与具体医学阈值必须来自经过核对的证据，本文件不生成新的临床结论。

### 第二步 先准备评测规范 再扩数据

从真实用户意图整理题型：别名、口语改写、否定、分型不明、生熟形态、同料不同工艺、剂量依赖、冲突、撤回和无答案。每题标注原文证据命题、必要限定、允许结论和应返回状态。先明确标注规范，再由独立标注与裁决建立数据；不要让20道编辑题同时承担调参、验收和泛化证明。

**产物**：200题候选池、按问题簇和来源分组的开发及冻结测试清单、标注分歧记录。已知资料上的未见问题测试与新增来源测试分别报告。

### 第三步 来源登记和资料解析

复用现有来源表，登记机构、标题、原版本日期、URL、核查日期、来源hash、状态和允许保存的范围。国家指南、成分样品研究和烹调机制资料类型分开，不能把机构权威性直接转换成任何结论都可执行。

解析先保留结构与原文定位；扫描表格必须目视复核。已有知识库正确保留了指南分类与实测样品、摘要依据与全文依据等差别。不要为充实规模把不能核验的数值填进去。

**产物**：可重建来源manifest、解析文本、原文span或页图定位、解析质量检查。项目已有7来源，接下来应补覆盖缺口，而非为了来源数盲目抓取。

### 第四步 设计实体与事实模型

实体至少区分疾病、成分、食品、食品类别和工艺；疾病分型、生熟干湿、加工状态作为身份的一部分。`alias_of`只表示同一身份；`contains`、类别、替代和工艺影响是其他关系。

事实的最小结构是“主体 → 关系 → 客体 + 适用条件 + 证据ID + 来源版本 + 直接性 + 状态”。成分机制不能自动成为食物建议，食物建议必须另有食物层面证据。`unknown`、未提供和否定事实都要区分。

**产物**：实体词典、关系类型、校验schema和冲突记录。当前已实现的 `KnowledgeBundle` 是起点，新的正式发布结构必须另行设计，不能偷偷把研究schema里的草稿限制放宽。

### 第五步 构建可复用切块器

当前53条证据是整理出的命题单元，不等于已经完成面向任意PDF的自动chunker。下一步切块器要把现有人工规则变成可复用流程：按章节与记录边界切，结论、否定、例外、单位和人群一起保留。

候选实验可以是child目标300至600个所选模型token、最大800；parent约1000至1800 token；跨自然段少量重叠。参数来自既有方案的实验起点，必须经新评测集验证，不能说当前线上按这一长度运行。

**产物**：切块器版本、tokenizer指纹、父子映射、原文定位、条件关联和坏切片回归。引用文本与增强检索文本分字段保存。

### 第六步 建中文词法基线

先优化当前受控别名与实体锚点：完整词边界、最长匹配、歧义候选、否定保留、食品形态分离。数据库中的GIN准备结构可以接SQL全文检索，但需要明确分词版本、词典和`simple`配置，使用参数化查询。

当前正则抽取连续中文词串，较长口语句可能被当作一个片段；疾病实体又会给该疾病多条事实相同分数。别名帮助部分例子命中，但尚未证明能稳健覆盖复杂改写。应加入同义短语、长句、未登录词与同分排序测试，不直接把此问题归因于Embedding模型不够强。

**产物**：A0当前应用内基线，A1改进词法基线，SQL查询与执行计划、中文困难题报告。PG排名不是BM25。[PG全文检索](https://www.postgresql.org/docs/17/textsearch-controls.html)

### 第七步 对照Embedding并解决在线编码

候选为BGE-M3 dense与Qwen3-Embedding-0.6B；分别锁revision、tokenizer、指令、池化、归一化和维度。BGE-M3官方为1024维、最长8192 token；Qwen0.6B支持最长32K与最高1024维可调输出。这些是规格，不能推出本机速度和项目效果。[BGE](https://huggingface.co/BAAI/bge-m3)、[Qwen](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)

先在可用硬件对公共资料离线编码，报告吞吐、峰值内存、失败与截断。在线query还要用同一模型，CloudBase函数不应未经验证直接加载权重。未确定无新增费用且符合资料边界的在线编码通道时，产品继续用关键词，不把文档向量建好当成线上向量链路完成。

**产物**：模型对照表、编码manifest、独立向量表、query接口和资源实测。这里的“零新增API账单”不代表标注、设备和维护没有成本。

### 第八步 召回 融合 重排与上下文

检索分成三个入口：已知规则证据按ID取回、受控关键词、可选向量。先用小库精确向量距离作为基线。各路候选以chunk ID去重，RRF只融合发现性候选；强制证据、反对证据和必要限定有独立保留策略。重排作为下一轮消融，只有改善困难题且预算允许才加入。

候选量可从每路20或40、融合后最多60至80、最终8至12个child试验，不能未经测量把所有上限同时打开。父节按需回取，最终是否足够取决于证据命题完整而非固定条数。[pgvector](https://github.com/pgvector/pgvector)、[重排模型卡](https://huggingface.co/BAAI/bge-reranker-v2-m3)

**产物**：每题各通道候选、融合排名、重排变化、最终证据包、总token和失败分层。公开构造集可存完整trace，个人健康正文不进入一般日志。

### 第九步 条件判断与真实菜谱绑定

引用的证据不是直接作用于菜名，而是通过“适用的食物或工艺指导 → 真实变体中的明列食品和做法”。当前目录以bundle为准，绑定需包括 `bundleId + bundleHash + recipeId + variantId + methodId`，不能外键指向尚未填充的规范化目录空表。

程序分别核对过敏忌口、库存、补买、疾病适用规则和工艺条件。缺量不普遍阻断定性建议；必要剂量、人群或工艺条件未知时，仅暂停受影响判断。避免项不被有益项抵消；多病种并集排除只能处理已适用的规则，不能替代疾病组合的专业验证。

**产物**：真实ID映射、条件执行器、规则证据完整率、变体和方法差异测试。当前 `recipeBindings:0` 是首先要补的落地缺口。

### 第十步 建受控Agent和工具契约

初期不增加自主写库工具。内部工具建议为 `resolveEntities`、`retrieveEvidence`、`loadEvidence`、`evaluateGuidance`、`matchCatalog`，只暴露当前状态需要的能力。模型可为缺失证据提出最多一次受控补充检索，不能修改用户确认的疾病、过敏和补买。

每次动作前校验schema、实体存在、权限、输入版本与预算。RAG正式发布前仅展示研究结果；不允许模型自行把draft批准成规则。线上不需要独立“医学专家Agent”投票；同源模型投票不会补足证据。[工具设计](https://www.anthropic.com/research/writing-tools-for-agents)

**产物**：状态转移表、工具输入输出schema、最大轮数、预算、取消与失败状态测试。详细接口草案见第三份文档。

### 第十一步 上下文管理与个人记忆

当前策略是消息条数和字符上限，暂不称为压缩。增量方案先结构化已确认状态与近期窗口，再为更早历史生成会话内摘要；硬限制始终从权威偏好读入。摘要不能覆盖Key、过敏、用户授权或新确认。

不因引入框架自动保存完整健康对话。当前个人资料只保留既有授权字段，原始聊天仍仅内存；若要跨设备续聊，需要单独定义资料保留策略。研究摘要与证据也不能混入个人偏好。[上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

**产物**：预算器、摘要schema、不变量校验、token总账、压缩对照和退出清理验证。

### 第十二步 验收 灰度与持续维护

先本地离线研究与构造测试，再真实PostgreSQL多连接、CloudBase有界RPC和获授权的小样本模型联调。上线前检查专业范围、事实和规则发布、菜谱绑定、撤回及账户隔离；按功能开关灰度。出现质量或技术异常时关闭受影响健康分支，普通推荐保留明确入口。

持续维护包括来源更新、增量建库、撤回水位、失败回归与模型版本漂移。不要仅用“测试全绿”替代线上运行观察，PGlite也不能证明真实PG锁竞争。

**产物**：版本清单、灰度及回滚步骤、监控指标和故障演练记录。Agent最终验收要看实际状态和副作用。[Agent评测](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 四 切块与检索的具体设计

### 一个可以在白板上讲的切块例子

以下是构造材料，用来解释工程机制，不是真实医学指导：

```text
标题 人群A的食品F选择
结论 在条件C满足时 可优先选择F
例外 若条件D成立 上述建议不适用
表格 F中的成分X 样品状态S 数值V 单位U 基准B
脚注 样品仅代表该来源的S状态 不代表其他加工状态
```

错误做法是把结论切成一块，例外切到下块，表格只保留数值。正确做法是给命题设置 `required_context_ids`，保证结论与C/D一起取回；表格记录独立保存S/U/B和脚注；标题可以进入retrieval text，引用仍指各自原文span。

```json
{
  "evidenceUnitId": "ev:F:C:v1",
  "sourceVersion": "v1",
  "spanHash": "sha256 of original span",
  "retrievalText": "标题 实体别名 原文命题",
  "requiredContextIds": ["ev:F:exception:D:v1"],
  "parentId": "section:F:v1",
  "entityIds": ["food:F", "condition:C"],
  "originalText": "可核对的原始短摘",
  "reviewState": "draft"
}
```

这是目标契约示意，不是现有 `KnowledgeEvidence` 已包含全部字段。新字段应走schema版本迁移，不能直接覆盖交付知识包。跨chunk版本评测以稳定证据命题或span为标注对象，解决“换切片后Recall分母变了”的问题。

### 中文查询处理流程

保留原问 → NFKC副本 → 受控别名最长匹配 → 输出候选实体和形态 → 保留否定与比较关系 → 生成分词query和语义query → 必要歧义澄清。不得把“糖尿病”自动确认为成人2型，也不能把“香菇”自动确认为鲜或干样品。

不带空格的“痛风牛奶能不能喝”在本次探针仍能依靠别名找到牛奶关系，但也出现同疾病无关事实占候选的情况。要用大量改写题衡量候选噪声和排序，不能凭一例命中宣布中文检索已解决。

### 为什么不直接让模型判食材安全

语义检索只找相关内容，机制证据、样品测量和指南建议性质不同。项目采用显式关系和条件，模型发现的新边先作为候选，核验后才能进入规则。禁止从“含X，X可能有益”直接推出“吃F能治疗疾病”；也禁止从“可能不利”直接升级成任何量都不能吃。

## 五 数据存储与版本一致性

### 当前结构可以复用什么

独立 `health_kb` schema 已包含来源、实体、别名、证据、事实、事实证据关联、规则草稿、冲突、撤回和索引manifest。核心ID和外键可复用，JSONB承载扩展对象，schema负责合法性。现有研究DDL显式限制 `clinical_release IS NULL`、规则draft、审核pending及无Embedding；这正好隔离了研究与执行。

目标正式发布应新增独立审核和发布层，并提供只读取approved快照的服务端视图/RPC。不要修改研究表CHECK使其既存研究又存正式状态，避免历史证据含义被改变。向量是证据的派生索引，应新建健康证据向量表，不塞进菜谱变体Embedding表。

### 版本如何同时生效

一次执行绑定知识bundle、来源/证据、规则release、词典、索引manifest、菜谱bundle与hash以及本餐输入版本。开始时读一致快照，结束前复核权威发布指针与撤回水位。任何关键版本变化时重验或返回过期，不输出基于旧输入的成功结果。

回滚指向旧release时仍应用最新撤回集合。缓存键包含版本只能降低串用概率，不能代替输出前的撤回检查。已经拿到的证据如果在请求进行中撤回，要在最终校验阻断受影响结论。

### 个人数据怎样隔离

公共知识只有公共资料与可核验关系；账户存既有授权的健康自述、目标、偏好和加密Key；完整聊天仍在会话内存；操作账本只存不可还原绑定摘要和必要状态。查询向量与最终推荐不默认形成公共训练数据或推荐历史。

模型输入构造也应体现信任边界：当前代码对个人疾病和本餐JSON使用固定system模板包装，未来可将这些资料放在独立、明确标注的用户数据区，避免信任级别混淆。需要结合模型协议测试后再改，不能仅凭角色名断言当前已发生泄露。

## 六 已有真实难点与未来实验怎样分别讲

### 案例一 食材同名与形态导致证据混用

**现有可核对问题**：资料中鲜香菇和干香菇、干豆与特定豆制品不能用同一数值代表。不同来源对鲜香菇也有分类范围与样品测量差异。

**已有处理**：身份分开，保留样品和分类性质，冲突互联，不取区间中点或简单平均；未限定“香菇”不静默选一个形态。检索返回研究依据与冲突，不批准执行。

**面试说法**：“我把身份对齐和事实推导分开。别名只帮助找到实体，形态和来源基准决定事实能否使用。遇到冲突保留来源差异，系统返回覆盖或适用问题。”

**后续证据**：增加口语别名、类别展开和真实菜谱形态绑定的困难题；当前尚无完整覆盖率。

### 案例二 来源正文和表格不一致

**现有可核对问题**：知识库记录某论文正文与表格的两项数值顺序不一致。

**已有处理**：本批排除这两项数值，等待核验，保留冲突记录。没有让模型选择一个“看起来合理”的值。

**面试价值**：说明资料治理如何处理无法自动裁决的事实；可展示 `conflicts.jsonl` 和来源定位。不能说发现了论文错误或已经获得作者确认。

### 案例三 烹调减少不等于整餐减少

**现有可核对问题**：某成分从肉块迁移到煮液，肉块变化不自动代表喝汤后的整餐变化。

**已有处理**：工艺条件和“弃汤/连汤”等需要区分，项目解释与直接实测分开，未补造温度、分钟和损失率。此处是证据适用性建模，不是已测出每道菜的实际成分。

**追问答法**：先说明输入、介质、是否弃液、输出基准，再解释原料组成与成菜摄入之间缺哪些依据。

### 案例四 模型建议不能越过用户意图

**当前机制**：健康情况与目标按既有设置保存；接受“推荐、少选、避开”各类偏好、保存AI去疾和应用本餐分别遵循现有交互。程序匹配真实图鉴，模型不能编造目录外菜谱或修改补买人数。

**技术重点**：模型建议是候选；真实目录、限制过滤和写入由程序校验。用户确认应绑定具体提案及版本。已有行为不需要为了展示Agent重新改成每一步都弹确认。

**待补验证**：过期提案、两页并发修改、模型回复晚到及输入改变后的执行矩阵。

### 案例五 重复请求可能重复消费

**当前机制**：公网健康聊天用PG RPC做共享单次认领和账号限额；外部等待不持有数据库长事务。客户端超时、断流或未知结果不自动重发。模型响应凭证来自供应商返回，不生成假request ID。

**面试说法**：“我把本地重复点击、跨实例认领和供应商结果未知分开处理。数据库能保证同一操作的原子认领，但不能替外部供应商保证恰好一次计费。”

**待补验证**：真实多连接及云函数重复请求、调用后进程崩溃等故障演练，不能拿PGlite单连接测试代替。

### 案例六 有知识库不代表已经有RAG产品

**现有状态**：研究事实、引用和规则草稿已经可重建，但没有正式规则发布和真实菜谱绑定，也未部署query向量编码。

**面试说法**：“我先完成可追溯研究数据和关键词基线，再把正式规则、目录绑定与评测作为下一阶段验收。没有把建表或研究检索结果直接当成健康推荐上线。”

**下一步**：先做一个真实变体和方法的闭环，再扩向量对照；这比先选图数据库更能推动交付。

### 三个适合后续真正做出成果的实验

**实验A 召回改进**：A0当前基线、A1中文词法、B增加dense+RRF、C再重排；固定题集，报告事实和必需证据覆盖、nDCG、条件错配与P95，选择最小有效方案。

**实验B 上下文压缩**：同一多轮构造任务比较硬上限、滑窗和结构摘要；统计完整会话含摘要成本，验证硬限制、确认、最新更正和未完成任务保留。

**实验C 可靠执行**：同operation并发、同ID异输入、模型晚到、用户取消、Key变更、证据撤回和目录更新；检查账本、状态和真实副作用。每个实验都保存配置、输入hash和原始结果。

以上是待做实验，不是历史实绩；完成后才能把“设计了”升级为“实现并验证了”。

## 七 面试三分钟讲述稿

“我做的是拾味，面向家庭做饭。用户输入食材和偏好后，系统从已发布菜谱里选择可做的菜，程序负责过敏忌口、库存和套餐一致性，不让模型自由编造配方。

项目已经有React和TypeScript前端、Fastify后端、CloudBase部署及PostgreSQL账户和内容存储。健康方向目前有个人Key的DeepSeek对话入口，能够整理用户自述与食材建议，并匹配真实图鉴。公共RAG部分完成了本地研究小库，包含7份来源、53个证据单元和155条关系，规则仍是草稿，没有直接用于线上疾病筛选。

我重点想展开的是知识建模和执行边界。疾病与成分关系不能直接推出吃某食材有益，所以把来源、证据、事实、定性规则和个人资料分开。比如鲜干形态和指南分类、样品测量不一致，我保留各自身份、条件和冲突，不做简单平均。烹调时还要区分成分从原料迁移到汤中，不能把原料降低说成整餐摄入降低。

检索从结构化和关键词基线起步；20道编辑回归目前都能在前5条找到全部预期事实，但这不是独立测试集的准确率。下一步先补真实菜谱变体绑定和独立评测，再比较BGE、Qwen向量和重排，只有能证明增益才加入线上。

工程上还处理了单次调用认领、预算、取消和模型输出校验。我的判断是这个项目应保持外层确定性流程，在查询理解和证据发现内部加入受限Agent，这样能解释每项结果，也便于控制费用和验证失败。”

这是一份基于当前仓库的讲述模板。“我重点负责”的模块必须换成你本人真实负责的范围；不能由文档代替个人经历证明。

## 九 项目专项追问与回答

### 为什么不用纯向量检索

“本项目需要疾病分型、食品形态、条件和撤回的精确约束。向量负责发现相关片段，不能决定某食材是否适用。结构化关系负责身份与已核验规则，关键词补精确术语；加入向量前先测它能补哪些改写题。”

**再追问**：向量效果很好也不能替代什么？答：正式发布、身份权限、用户确认、过敏忌口、规则适用和最新撤回复查。

### 为什么先用PG而不选图数据库

“当前关系规模小且路径明确，SQL连接可以表达疾病、成分、食材和工艺关系。复用PG还能减少同步和回滚复杂度。只有可变深度路径、规模或查询负载显示真实瓶颈时才比较图数据库。”

**再追问**：图是不是更适合多跳？答：表达方便不等于总成本更低，需结合路径类型、查询、事务与运维对照。

### 当前chunk怎么做的 与自动切块有什么区别

“现在的53条是人工整理且可定位的证据单元，重点保留命题、条件和来源。通用自动chunker尚未完成。计划按指南条款、表格记录和工艺命题切，child定位、parent补条件；长度用token测并做消融。”

**再追问**：为什么不用固定500字？答：会割裂例外和表头；可以留作简单对照，但不能默认最优。

### 为什么Embedding还没定 能不能说用了BGE

“可以说BGE-M3和Qwen0.6B是对照候选，不能说已部署或已经提高了Recall。当前缺实际硬件与线上query编码验证，我会先做公共语料实验，线上仍保留关键词。”

**再追问**：选型维度是什么？答：困难题、条件错配、中文与混合术语、P95、峰值内存、建库及在线费用、版本与资料边界。

### 召回不到证据怎么办

“先判定是否知识覆盖、身份解析、索引或技术故障。最多做受控改写补检索，仍缺就返回具体不足；不会把检索没找到变成安全，也不会因一个无关营养量缺失关闭所有健康信息。”

**再追问**：何时必须停止推荐？答：必要避忌条件或执行依据无法核验时，停止受影响判断或排除相关变体；不把技术故障当无结果。

### 为什么现有20题不够

“题来自建库过程且多为直接实体词，验证基础编辑正确性有用，但不能代表口语改写、未见来源和真实用户分布。下一步做分组冻结集，人工补相关证据标注和无答案状态，避免同义题泄漏。”

**再追问**：200题够不够？答：是初期可执行规模，不保证总体代表性；要按风险分层、报告分母与区间，持续补失败类型。

### 怎样计算上下文压缩的收益

“当前没有结构摘要，只有限长防护。新增压缩会先固定多轮任务，记录整段会话所有输入、输出和摘要token，并测硬限制与新更正保留。只看某一轮输入缩短不能说明总费用或质量改善。”

**再追问**：能保存摘要长期记忆吗？答：当前完整聊天不持久化，会话摘要也只在内存；跨会话保存需要符合用户明确资料策略。

### 健康建议冲突如何解决

“先核对适用人群、来源版本、食品形态、剂量与工艺，显式保留支持和限制。明确适用的避免项不被有益项抵消；无法裁决的专业冲突返回不足或待复核，不能简单让模型投票或永远取最严。”

**再追问**：所有疾病分别通过，组合是否通过？答：不自动通过，组合条件和相互影响需独立定义支持范围。

### 为什么不让模型生成新菜谱

“目前产品承诺固定已发布配方与受控变体，量和步骤需要有据。模型可以解释选择、理解检索意图，但目录资格、真实方法与硬限制由程序决定。自由生成会引入无法验证的用量、成分与烹调假设。”

**再追问**：这样还算Agent吗？答：当前主要是工作流；是否加入受限自主检索取决于实际收益，项目价值不依赖名称包装。

### 如果用户说删除知识库怎么办

“问答进程不持有知识库删除权限，也不向模型暴露管理员工具。检索文本中的指令按数据处理，写操作由独立授权流程控制。单纯prompt拒绝只是辅助，最终由权限与执行器保证。”

### 云函数如何保证一次调用

“PG负责共享认领，固定身份与operation绑定；不依赖某个实例的内存。数据库认领与供应商执行是两个边界，超时可能已经消费，因此不自动重发。当前需要补充的是真实故障窗口和多连接演练。”

### 为什么有AI偏好还需要RAG

“用户接受的偏好代表个人意愿，不是公共医学事实。当前模型建议也没有声称经过RAG核验。RAG补可追溯证据与适用条件，正式规则才能参与健康判断；二者需要在数据字段和UI来源标记上区分。”

### 换模型怎样避免旧摘要污染

“用模型配置版本和摘要来源版本绑定上下文，重新计算预算，硬状态从权威资料读。用户更新过的疾病、偏好和确认以最新版本覆盖；不能简单复用旧模型隐藏状态，也不能自动切供应商导致资料流向变化。”

### 你还缺什么 为什么值得继续做

“最关键缺口是实际菜谱绑定、独立评测、正式规则与撤回发布、在线query编码和压缩验证。我优先把一条证据到真实变体的闭环做完，再测检索扩展；这样每次迭代都能形成可展示的结果，而不是只增加技术名词。”

## 十 简历写法与演示方式

### 当前可以使用的简历表达

“开发家庭菜谱推荐应用，基于React、TypeScript、Fastify与PostgreSQL实现固定目录推荐、食材限制、库存与套餐一致性核验；接入个人Key模型对话和程序化真实菜谱匹配。”

“构建可重建的健康公共研究知识库，整理7份来源、53个证据单元和155条条件化关系，分离证据、事实、规则草稿及个人资料，支持来源定位、冲突保留与撤回；完成20道编辑检索回归。”

如确由本人负责，可另写“设计模型输出校验、共享单次认领和输入版本绑定，限制重复执行及未知结果自动重试”。所有表述以个人实际贡献为前提。

### 实现后才能写的表达

“部署混合检索提升Recall”“上下文压缩节省X%费用”“多Agent自主执行”“正式疾病推荐上线”“真实PG并发故障恢复通过”均需完成相应验证。第三份方案提供实验和验收标准，数值不预填。

### 五分钟演示脚本

先演示普通模式一条正常推荐和一条硬限制拦截，说明真实目录；再展示健康聊天的来源类型和用户接受动作。第三步运行本地研究查询，展开引用、条件与冲突，显示 `executionAllowed:false`。第四步展示一个来源到关系的定位，以及20题复核的真实口径。最后打开目标架构与一条优先实施任务，说明已有成果与下一步。

不要把研究查询输出与当前线上聊天拼成已经接通的同一链路；演示环境、构造模型响应和真实供应商调用分别标注。
