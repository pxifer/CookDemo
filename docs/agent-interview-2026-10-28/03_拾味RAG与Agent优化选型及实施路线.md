依据项目现状和面试追问形成的实施方案

方案日期 2026年10月28日

后续实施更新：用户继续授权优化和疾病扩库后，v2已落地A1词法、必需证据、不可变快照/缓存及跨版本撤回；当前为11来源、98证据、260关系、8个疾病实体和50题编辑回归。本文以下表格保留原规划与当时基线；已实现范围以[实际优化复核](../../agent-design/optimization/health-rag-optimization-v2.md)为准，配套原DOCX仍是此前规划快照，没有冒充同步修改。

本文是对已有健康RAG方案的具体化与更新。除明确标为“本次文档修正”“本次只读复核”的部分，其余为后续实施设计；没有执行云端迁移、下载权重、新增收费资源、启用正式疾病推荐或改动运行时代码。实验参数是候选值，验收门槛是待冻结目标，均不冒充实测结果。

## 二 与旧方案相比的实质变化

1. 不再把“首主题尚未确定”作为下一步：三主题研究库已建成，应直接补审核、绑定和评测。
2. 明确当前查询在应用内执行，不把GIN准备索引描述成SQL全文基线，更不称为BM25。
3. 新增A0与A1区分：保留当前检索为A0，先改进词法和实体契约形成A1，向量相对A1对照。
4. 保持研究DDL的draft和pending限制，正式审核和发布另建层，避免改变历史研究包含义。
5. 评测单位从可变化chunk ID提升到稳定证据命题或原文span，解决切块消融不可比的问题。
6. 撤回、事实与规则版本、菜谱bundle、模型编码协议形成一致执行快照；输出前再验权威水位。
7. 从“将来做压缩”落到摘要schema、权威硬状态、会话内存范围和全任务成本统计。
8. 明确在线query向量化是上线依赖；无合规可承载的编码通道时保留词法路径。
9. 将“多Agent与框架”改为有条件引入；线上先实现固定状态机和只读受限检索。
10. 更新与现有个人Key聊天一致的能力说明，保留单次调用、不自动重试和资料保留约定。

## 三 技术决策与替代条件

### 决策一 在线保持TypeScript Python用于离线资料处理

当前线上和业务规则主栈均为TS。检索、状态机和校验先保持同栈，降低双服务协议与部署成本。Python继续承担PDF处理、标注辅助和离线模型评测；只有Embedding在线服务明确需要且已验证资源后，才封装独立境内编码服务。

替代条件是既有运行时无法承载编码且专用服务在预算与资料边界内有明确收益。不能为了面试出现Python关键词而把已稳定业务重写一遍。

### 决策二 PostgreSQL是权威存储 pgvector是可选派生索引

公共事实、证据关系、批准快照、撤回和真实目录绑定需要一致性。复用PG能够减少跨库双写与删除回滚链路。小库先精确距离检索，ANN仅在目标硬件实测P95超预算时加入；不是按“超过多少条必上HNSW”机械判断。[pgvector说明](https://github.com/pgvector/pgvector)

Milvus、Qdrant等独立服务保留为未来容量方案，比较时必须加入备份、权限、过滤、撤回、索引重建与人员成本。当前不新增服务。

### 决策三 实体与结构化规则先于相关性排序

疾病分型、食材身份、形态和适用条件由结构化层明确。检索负责发现内容，规则执行不依赖向量分数。精确规则必需证据按ID读取，不给top-k“抽奖”决定是否包含禁忌条件。

别名是身份对齐，食品类别和组成是事实关系；它们分别建模。类别展开在有受控映射且版本明确时加入，不能从语言相似度推断“某复合调料含有某成分”。

### 决策四 先升级中文词法 再比较dense与RRF

A0保留现有 `searchKnowledge`。A1实现受控词典最长匹配、歧义结果、否定与比较关系、可解释排序，并将小库应用内路径与SQL全文路径用相同输入输出契约对照。PG使用预分词token、`simple`、GIN和`ts_rank_cd`，称为PG全文基线。[PG官方文档](https://www.postgresql.org/docs/17/textsearch-controls.html)

BM25仅在开发集证明长度归一化或稀疏召回存在收益、且运行环境支持后再引入。不能为了和面经答案一致而把现有排序改名。

### 决策五 BGE与Qwen对照 不预宣布赢家

首轮候选为BGE-M3 dense和Qwen3-Embedding-0.6B，均先用1024维实验；BGE的稀疏、多向量能力不同时引入，降低归因难度。Qwen的query指令和输出维度要锁定；不同模型即使同维也必须独立索引。[BGE模型卡](https://huggingface.co/BAAI/bge-m3)、[Qwen模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)

以本项目困难题、条件错配、P95、峰值内存和在线运行代价选择。公开榜单只用于候选筛选。语料少时A1可能已经足够，保留不用dense的结果是有效决策。

### 决策六 重排作为可开关实验

候选BGE reranker v2 m3仅对较小候选集执行。检索不到的内容不能靠重排补回；长输入截断也可能删限定。若整体质量不降且困难题有稳定收益，且总预算满足，再开启。[重排模型卡](https://huggingface.co/BAAI/bge-reranker-v2-m3)

不把重排score当事实可信概率；运行时可在非必需重排超时时退回未重排的已完整证据集合，而非跳过规则校验。

### 决策七 研究层与正式发布层分离

现有研究表CHECK明确只能存研究状态，继续保留。新增审核记录、批准事实版本、可执行规则版本、真实目录绑定与release manifest。发布层显式引用研究证据，不让模型或普通用户修改审核结果。

如果暂时没有专业审核，就继续做公共研究检索、流程和评测开发；不因此阻止工程进展，也不将研究输出开放为正式疾病筛选。

### 决策八 单状态机加受限检索Agent

外层流程固定，内部只读检索可有限改写与补检索。首个实现用显式TS类型和状态转移，不急于引入框架。LangGraph可作为未来长任务、复杂中断恢复的候选，但其默认持久化不能覆盖当前健康聊天的内存保留约定。[LangGraph持久化](https://docs.langchain.com/oss/python/langgraph/persistence)

多Agent只在独立任务确有并行收益时实验。当前不建中心调度平台或“多个医学专家投票”路径。

### 决策九 模型接口锁协议与实测 不自动切供应商

当前个人Key聊天固定DeepSeek `deepseek-flash`，本轮查官方文档确认该名称仍可用。型号别名实际后端可能变化，因此记录请求别名、响应model、配置版本、日期及非敏感usage，定期回归；不能仅靠别名声称权重固定。[DeepSeek官方接口](https://api-docs.deepseek.com/)

后续增加工具调用或thinking模式前做能力探针和schema测试，不凭“兼容API”假定所有参数一致。失败不自动换供应商；当前个人Key单次尝试约定继续有效。

### 决策十 上下文摘要只处理历史 硬状态从权威来源重建

先引入token预算、近期窗口和可丢弃工具结果，之后增加会话内结构摘要。过敏忌口、用户接受项、待执行提案、操作状态和版本独立保存，摘要无权修改。压缩后检查不变量，失败就保留旧状态并缩减可选内容。[上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

### 决策十一 优先有界RPC 不暴露任意SQL

CloudBase现有Data API读取不等于已经支持向量SQL。优先验证固定能力RPC，检查身份、维度、候选数量、发布状态和超时；若平台能力不足，再评估最小权限原生PG通道。浏览器不能拿管理员密钥，也不能指定任意SQL或供应商URL。

### 决策十二 幂等与执行未知分开

沿用共享原子认领；相同operationId不同输入拒绝，认领后提交再调用模型。预算和Key版本绑定输入指纹，外部结果未知则不自动补发。新增工具执行也按只读、确定失败、结果未知分别处理，不承诺跨服务exactly once。

### 决策十三 公共知识与个人资料隔离

公共知识库不存用户query向量、健康对话和最终推荐历史。账户只存既有授权字段与加密Key；完整聊天及会话摘要仅内存。通用日志不记录个人健康正文或参数。框架和遥测默认采集必须关闭或显式裁剪。

### 决策十四 相关性和健康执行各自评测

检索改善不代表健康判断改善。分别报告命题覆盖、必需限定覆盖、条件错配、引用有效、规则执行和真实菜谱约束。LLM judge辅助筛查，关键规则由可执行断言与专业复核支撑。[Ragas](https://arxiv.org/abs/2309.15217)、[Agent评测](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 四 存储优化与表结构建议

### 数据分域

| 数据域 | 权威保存位置 | 主要内容 | 保留和访问原则 |
| --- | --- | --- | --- |
| 公共研究 | 既有health_kb与不可变bundle | 来源 实体 证据 关系 草稿 冲突 | 保留研究状态 来源可核对 |
| 审核与正式发布 | 拟新增health_publish | 审核记录 批准版本 规则 绑定 release | 后台受控写入 产品只读批准快照 |
| 检索派生 | 拟新增health_index | 切片协议 token索引 向量 编码manifest | 可重建 不成为事实权威 |
| 菜谱内容 | 既有内容bundle与发布结构 | recipe variant method和hash | 绑定实际版本 不假定空表已填 |
| 个人设置 | 既有账户加密存储 | 健康自述 目标 已接受偏好 Key | UID隔离 既有授权字段 |
| 会话 | 当前页内内存 | 对话 临时摘要 证据包 | 不自动跨会话持久化 |
| 操作与观测 | 既有认领表及必要扩展 | ID HMAC 状态 时间 usage | 不保存正文 Key或查询向量 |

### 关键字段和约束

`health_publish.approvals`记录对象ID及不可变版本、证据集合hash、审核角色、结论、时间和撤销，不把“source_checked”等同临床批准。`health_publish.rule_versions`记录动作、适用条件、事实版本及所需证据。`recipe_bindings`包含真实bundle/hash/recipe/variant/method，并保存受控食品和工艺映射的版本及核验状态。

`health_index.manifests`至少记录知识包hash、chunker、词典和分词器版本、模型revision、tokenizer、query instruction、池化、归一化、维度、距离、编码实现版本、创建状态及完整性统计。把这些字段序列化后hash成 `embeddingProtocolHash`，查询和文档协议不匹配直接拒绝。

`health_index.evidence_embeddings`用 `(manifest_id,bundle_id,evidence_id,chunk_id)`标识派生记录，并对当前研究证据建立复合外键或受检映射。维度用显式列类型约束。不同模型独立manifest与物理索引，不能通过一个model字符串在同一近邻搜索里混查。

热过滤字段如release、state、实体和外键放在关系列；复杂条件和定位保留JSONB加schema。来源原文件按复用范围保留本机核对副本或受控对象，产品不默认公开全文。变化走新迁移和新schema版本，既有迁移checksum不改。

### 参考SQL仅用于设计评审

```sql
-- 设计草案 未执行 不是对现有研究DDL的覆盖
CREATE TABLE health_index.evidence_embeddings (
  manifest_id text NOT NULL,
  bundle_id text NOT NULL,
  evidence_id text NOT NULL,
  chunk_id text NOT NULL,
  protocol_hash text NOT NULL,
  embedding vector(1024) NOT NULL,
  PRIMARY KEY (manifest_id, bundle_id, evidence_id, chunk_id),
  FOREIGN KEY (bundle_id, evidence_id)
    REFERENCES health_kb.health_evidence_chunks(bundle_id, id)
);
-- 小库先在发布范围内精确排序
-- production查询还必须JOIN正式发布快照并检查来源和撤回
SELECT chunk_id, embedding <=> $2::vector AS distance
FROM health_index.evidence_embeddings
WHERE manifest_id = $1 AND protocol_hash = $3
ORDER BY embedding <=> $2::vector
LIMIT $4;
```

这段SQL只展示类型、绑定与距离，不包含完整发布授权和撤回过滤，不能原样放入生产。RPC函数参数中的 `vector(1024)` 不应被当作唯一维度保障，应显式检查 `vector_dims`、非零/有限值、协议hash与上限；函数参数typmod不能替代业务校验。

### 撤回与原子发布

新增发布流程是“准备不可变证据与规则 → 完整性检查 → 冻结manifest → 切换active release指针”。撤回是全局权威状态，先阻止可见与执行，再清理索引；回滚也读取最新撤回。请求开始锁定快照，最终输出复查水位，受影响内容变化时重验或返回 `stale`。

必须覆盖的撤回目标包括bundle、来源ID/版本/hash、证据、事实ID/版本、规则和绑定。定义依赖展开，不能只删除向量后就认为规则已停用。

## 五 检索契约与算法细化

### 统一输入输出

```ts
// 目标内部契约 尚未实现
type RetrievalRequest = {
  operationId: string;
  query: string;                    // 仅请求内
  queryVersion: string;

  confirmedContext: Record<string, string | 'unknown'>;
```

前端不能自行传required证据来绕过规则，不能仅根据 `state:complete` 判断可执行。完整是检索结果集合的状态；正式release、适用规则和真实绑定全部满足后才可能执行。研究接口始终保持 `executionAllowed:false`。

### A1词法流程

1. 保留原文，生成NFKC和大小写规范化副本；不能删除否定。
2. 词典做最长候选匹配，完整实体和短词冲突时优先受控全称；保留多个合理候选。
3. 疾病分型、食品形态和工艺条件不明时输出歧义，禁止静默选取。
4. 结构化实体检索与关键词检索分通道输出，不再用一个不透明总分同时承担身份与相关性。
5. PG全文按标题、实体和原文设可解释权重，应用基线保留作一致性对照；排序同分以稳定ID收尾。
6. 为长句、短词碰撞、括号、别名、拼写错误和未登录词建立回归，错字纠正只作候选，不改权威身份。

### 混合召回与RRF

候选发现的两路先各试top20和top40；按稳定chunk去重后最多60至80条。RRF候选 `k0∈{20,60}`，权重先相等；只在开发集比较。多query结果按实体和来源合并，避免同一来源的近重复片段挤占名额。

强制证据与必要限定在单独集合保留；候选发现按预算截断不能让它们消失。反对或限制证据要能被召回和展示，但“每个方向机械各留一条”不等于有证据支持。最终上下文选取以命题完整和适用性为准。

### HNSW启用条件

先测精确扫描在过滤后记录量、P50/P95和资源；只有性能成为瓶颈，才对照HNSW官方默认起点及 `ef_search`曲线。ANN近邻召回与业务证据Recall分开报告。过滤后的不足k、迭代扫描、精确回补必须测，托管平台扩展版本与RPC会话参数必须实际核验。[过滤机制](https://github.com/pgvector/pgvector#filtering)

### 上下文证据装配

优先放当前任务、适用硬状态、必需证据与限定，再放发现性证据。每片有ID、来源、版本、条件、原文定位和短文本。模型不能看到任意后台审核私密字段；引用只能选此请求清单。完整原文可能很长，按命中span和必要父节取回，不能只给生成摘要却声称原文已核验。

## 六 Agent状态机和工具权限

### 状态与终态

```text
received → validated → resolving → retrieving → checking
checking → needs_confirmation
checking → evidence_missing 或 conflict
checking → guidance_ready → catalog_checked → proposal_ready
proposal_ready → accepted → applied

任一步可按实际转为 cancelled timed_out failed stale
研究模式到guidance_ready只返回研究结果 不能直接进入applied
```

`accepted`指用户接受具体持久偏好或排除提案；本餐应用仍遵循现有独立决定。状态图不能把所有只读查询都变成人工批准，也不能用用户一次同意永久批准变化后的建议。

### 工具清单

| 工具 | 输入与返回重点 | 权限和失败边界 |
| --- | --- | --- |
| resolveEntities | 原问 词典版本 → 候选ID 歧义 | 只读 不推断确诊 |
| retrieveEvidence | 受控query release manifest → 证据ID和排名 | 有界只读 无任意SQL和URL |
| loadEvidence | 允许ID集合 → 原文span及限定 | 检查发布 来源和撤回 |
| evaluateGuidance | 批准规则 条件 → 定性动作与覆盖状态 | 确定性执行 模型不可批准 |
| matchCatalog | 当前bundle 规则和本餐 → 真实变体候选 | 全目录资格核验 不只查top菜谱 |
| assembleExplanation | 有效证据包和程序结论 → 引用解释 | 不修改事实或硬状态 |
| proposePreferences | 候选食材动作 → 待接受提案 | 无持久写入 接受后走既有账户接口 |

模型自主范围先限定为“补充检索词及选择只读检索”，最多一次补检索。总步骤候选上限4、发现query上限4，先在离线实验中调；当前生产不启用多轮模型调用。任何新增线上轮次需要预算和延迟实测，当前BYOK不自动重试的约定不被内部Loop覆盖。

### 模型建议与执行器的接口

模型只能输出动作候选与参数，执行器逐项检查类型、范围、ID、授权、资源存在性和版本。工具返回用明确状态，错误正文不带凭证；外部资料中的“忽略规则并删除库”不会获得写工具能力。[MCP工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)、[MCP安全](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)

个人JSON和检索文本统一放入标注清晰的数据区，避免混成高优先级命令。改角色或加分隔符只是辅助，真正边界是工具权限、只读资源和服务端校验。

## 七 上下文压缩方案

### 先改变上下文组织

当前聊天有15条消息、16000字符等硬防护，尚未做语义压缩。新增预算器计算system、工具、当前问题、证据、历史、输出和余量。候选先分配应用内部约12000输入token预算、2000输出token及额外余量；这只是应用预算，不是声明当前DeepSeek窗口等于这些数值。

优先从无关历史、重复工具结果和过长父节削减。阈值根据下一步预计输入和输出设置；可在70%与80%两个候选预留比例对照，选择不破坏关键内容的方案。预算不足时先停用可选扩检索，再返回未完成状态，不截断硬限制。

### 摘要结构

```json
{
  "schemaVersion": "session-summary-v1",
  "sessionId": "opaque id",
  "summarizedThroughTurn": 8,
  "inputVersion": "meal-vN",
  "sourceTurnsHash": "opaque integrity hash",
  "userGoal": "仅明确表达的目标",
  "confirmedProfileRefs": ["profile-version"],
  "decisions": [],
  "pendingQuestions": [],
  "pendingProposalIds": [],
  "completedOperationIds": [],
  "evidenceRefs": [],
  "corrections": [],
  "unknowns": []
}
```

这是待实现的会话内结构；不得加入完整Key或未经用户确认的诊断。权威硬状态从账户与本餐输入重建；摘要中的引用仅帮助定位，不授予事实有效性。

### 压缩不变量

必须保留或每轮重建：当前目标、身份和会话归属、过敏忌口、用户已接受的偏好及排除、人数和补买状态、未解决歧义、有效确认、已完成操作、输入/知识/目录版本、证据不足和撤回信息。用户最新更正优先，旧字段必须失效。

摘要生成后比较字段集合、版本和引用；出现未经证实的新诊断、限制删除、已完成操作丢失或旧提案复活时拒绝使用。不要用另一个LLM说“没问题”代替确定性字段检查。

### 压缩评测与成本口径

构造不少于30个多轮任务，包括早期限制、后续更正、代词、取消、提案变化、切模型和长工具结果。比较现有限长、滑窗、结构摘要。全会话token为所有模型调用的输入与输出之和，包含摘要和失败调用；费用按缓存类别与供应商实际价格另算。

报告硬限制保留、当前事实正确、重复执行、任务完成、引用支持、总token、P95和失败。候选目标是关键构造集不发生约束丢失，并在任务质量不降的条件下降低总成本；不预设“必须省50%”。摘要仍只在内存，持久化策略不变。

### 标注记录

每题记录query、实体、明确与未知条件、金标准证据命题或span、相关性等级、必需限定、期待状态、允许动作和禁止推断。关键健康结论两人独立核对并裁决；若缺独立标注人员，明确标为编辑回归，不能改名独立测试。

对检索候选池取多方案并集补标相关证据，降低只认识一条标准答案导致的偏差。换chunker时重新映射稳定命题到片段，避免仅因切块数变化而让指标失真。

### 指标与建议门槛

主指标：证据命题Recall@20、nDCG@10、必需证据及限定全部覆盖率、条件错配率、引用定位和支持有效率。补充：无答案误接收、过度拒绝、实际目录资格、撤回漏拦截、P50/P95、峰值内存、输入输出token与完整任务费用。

建议冻结前讨论的目标：有答案冻结题Recall@20约95%以上；所有关键构造样例的必需证据、撤回和权限断言通过；引用ID与定位合法率100%。这些目标不能转换成临床安全率。80题测试无法精确证明总体95%，必须给出分母和置信区间，按风险题型单独看结果。

B相对A1有整体提升或在关键困难题有稳定增益且不降低其他关键指标，才值得引入。旧方案“至少提高5个百分点”不再作为硬门槛：基线已接近上限时该要求可能无意义。质量相近时优先低成本、易维护方案。采用配对bootstrap等方式报告不确定性；不为了达到目标修改冻结集。

### 性能预算与度量

首次联调前保留现有17秒应用截止；内部阶段必须共享剩余deadline。可先试数据库与检索整体P95 1秒内、非模型处理2秒内作为开发目标，真实SLO要在目标云环境冻结。上游模型、冷启动和限流会影响总延迟，不承诺稳定17秒内必成功。

不开真实个人请求保存来换指标。公共题可保存完整检索trace；个人请求仅存计数、阶段耗时、状态和非敏感usage。usage是消费记录线索，不直接等于用户控制台扣费。[DeepSeek接口说明](https://api-docs.deepseek.com/)

## 九 云接口 幂等与故障处理

### 有界RPC的部署前检查

RPC固定查询模板、限制top-k和输入长度、验证向量维度与协议；读取当前允许release并检查撤回。`SECURITY DEFINER`若确实需要，应固定安全search_path、显式限定对象、撤销PUBLIC执行、最小权限属主，并独立验证调用角色；不能信任客户端传的ownerId。

本机PGlite只验证结构和部分行为。真实PG需多连接检查锁竞争、事务隔离和查询计划；CloudBase需核对扩展版本、Data API类型和函数能力。原生PG连接也需连接池、超时和最小权限，不能把直接连接当无成本替代。

### 幂等绑定与不持久化正文

操作绑定身份、operation UUID、输入版本、配置版本、凭证版本及不可还原指纹；唯一约束确保原子认领。当前指纹已使用HMAC，扩展设计优先用凭证版本而非让Key进入更多处理链。只存最小操作状态，不落健康正文、query向量或完整证据包。

如果模型返回后响应发送前崩溃，不能保证用户一定拿到原回复；保持未知或已认领状态，允许用户显式新操作，但清楚说明不是恢复原调用。没有保存正文时不声称具备无损跨进程续聊。

### 必测故障矩阵

| 故障 | 正确行为 | 验证方式 |
| --- | --- | --- |
| 同ID同输入两个实例 | 最多一次认领 不重发供应商 | 真PG多连接和云入口 |
| 同ID不同输入 | 拒绝绑定冲突 | 检查状态无覆盖 |
| 上游超时或断流 | 未完成 不自动重试 | 构造上游与真实小样本分开 |
| 用户取消 | 传递取消 不采纳晚到结果 | 取消前后时序注入 |
| 输入或Key版本改变 | 旧结果不覆盖新状态 | 两个并发请求 |
| 证据在生成中撤回 | 输出前重新校验并阻断受影响结论 | 注入撤回水位变化 |
| 目录bundle更新 | 旧绑定不直接套新方法 | hash不一致样例 |
| 向量或重排不可用 | 必需证据完整可走词法 否则停止相关判断 | 分通道故障注入 |
| 规则条件未知 | needs_confirmation或证据不足 不假定正常 | 临床条件缺失样例 |
| 恶意文档要求删库 | 无写权限与工具 | 检查真实数据库未变化 |
| 服务器重启 | 不回放未知副作用 不伪造恢复聊天 | 崩溃窗口演练 |
