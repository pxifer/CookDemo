## 2. 阶段 0 新增或补充决定

### D0-01：未知忌口及无法分类限制暂停推荐

- 状态：已确认。
- 来源：本轮 Q1，用户选择“暂停并核对”。
- 决定：无法识别的明确忌口、无法分类的限制表达，先暂停推荐；保留旧限制，待用户归类、改写或主动移除后继续。
- 影响：补齐 PRD A-09；推荐入口和限制状态须覆盖此分支。
- 不扩展到数量未知：数量未知仍按原规则允许推荐并标未核实。

### D0-02：先准备可审定的正式内容包

- 状态：方向已确认，具体内容待落实。
- 来源：本轮 Q2，用户选择“先建可审定内容包”。
- 决定：先整理自有或获授权的菜谱、口味变体及食材关联信息，记录来源，形成可审定内容包。
- 影响：内容包作为后续覆盖、检索边界和验收讨论的依据。
- 尚未确定：实际来源、规模、清单、准入负责人及质量标准。PRD A-01 未全部关闭。

### D0-03：预留健康审核扩展点，审核不阻塞研发

- 状态：已确认。
- 来源：本轮 Q3。用户选择专业人工审核方向，并明确：
  “目前没有专业审核，开放一个楔子便于后期填补，但是目前健康专题开发不依赖于是否审核。”
- 决定：
  1. 健康审核采用具备相应资质或专业能力的人工审核方向，模型输出不作为审核凭据。
  2. 当前专业审核资源尚未落实。
  3. 技术设计预留后续填补审核能力的扩展点。
  4. 健康专题设计和开发不以审核完成为前置条件。
  5. 对用户开放继续继承 PRD 的逐项审核门槛。
- 影响：开发测试状态与正式支持状态需要区分；具体接口和存储方式待技术设计。
- 尚未确定：审核主体、标准、来源、疾病及组合范围、更新和失效流程。

### D0-04：游客允许本机收藏

- 状态：已确认。
- 来源：本轮 Q4，用户选择“游客可本机收藏”。
- 决定：游客可在当前设备收藏菜谱及口味，登录后同步到账户。
- 影响：关闭 PRD A-05；游客收藏不增加强制登录步骤，需要明确本机保存范围。
- 尚未确定：导入、去重及并发删除等具体同步细节。

### D0-05：游客允许主动保存默认，登录确认合并

- 状态：已确认。
- 来源：本轮 Q5，用户选择“本机保存并确认合并”。
- 决定：游客可在本机主动保存默认；登录时展示本机与账户差异，由用户确认合并；冲突期间不静默覆盖已有硬限制。
- 影响：补齐 PRD A-07 的游客保存及登录合并方向；本餐草稿和工作台临时修改的既有边界继续保留。
- 尚未确定：多设备持续编辑、离线修改及并发冲突的具体处理。

### D0-06：大陆优先，敏感数据境内处理

- 状态：已确认。
- 来源：本轮 Q6，用户选择“大陆优先且敏感数据境内”。
- 决定：中国大陆用户为首要服务对象；真实照片及健康／过敏资料仅在境内处理。
- 影响：模型 API、图片链路、第三方服务及相关存储和日志方案须按此核查。
- 尚未确定：短期保留、第三方处理细节及公开静态资源部署位置；现有 Demo 托管不等于正式方案选型。

## 5. 阶段 1：食品营养与健康知识数据架构决定

记录日期：2026-10-18。以下 D1 决定来自本阶段逐轮问题的用户回答及批准的阶段 1 方案，具体设计见 [data-knowledge-design.md](data-knowledge-design.md)。决定技术方向不表示数据已获许可、已导入、健康规则已审核或功能已开放。

| 编号 | 状态与决定 | 对设计的影响及保留边界 |
| --- | --- | --- |
| D1-01 | **已确认**：健康模式定位为避开有依据的饮食风险，不作为食补、治疗或绝对无害保证；只有某条经审核规则确需适用条件时，才按需询问最少信息，允许“不清楚” | 条件未知时停止依赖该条件的健康判断；不从疾病名称或泛化建议推断个人安全；继承 D0-03 正式开放审核门槛 |
| D1-02 | **已确认**：菜谱推荐为主功能，营养是展示参考，不保证与实际制作或摄入完全相同 | 普通菜谱与推荐不因营养缺项停用；普通重点热量、健康可展开营养，均注明参考口径 |
| D1-03 | **已确认**：按标准配方已知可食部分量计算，计入有明确用量的主料、辅料及调料，按标准份数分配；不推定烹调损失或实际摄入 | 需保留形态、计量基准、份量换算、参数及输入版本；标准营养换算不能证明用户库存已核实 |
| D1-04 | **已确认**：某配料缺一项营养记录或必要用量无法换算，该营养素整菜值显示“暂无法计算”；其他完整项目照常展示 | 不以部分和冒充整菜总值，不把缺失当零；营养缺失与健康规则依赖数据缺失分开处理 |
| D1-05 | **已确认的架构方向**：关系型数据库＋规则表＋有版本的知识文档；向量索引按需增加，首版不引入独立图数据库 | 结构化事实和审核规则负责执行，文档负责证据追溯；不预选具体数据库、RAG、LightRAG、模型或 Agent |
| D1-06 | **已确认**：首版仅使用免费且许可明确的数据，优先复用条件较简单的来源；Open Food Facts 等带衍生数据库复用义务的来源暂不接入首版 | 具体数据集、版本、用途和记录仍须逐项核验；公开可查不等于可批量入库；实际来源清单尚未定 |
| D1-07 | **已确认**：健康风险覆盖明确禁忌及条件性限制，条件的适用范围、计量和时间口径必须经审核；一般建议和证据不足另行记录 | 不将全天建议自行换成单餐阈值；缺少必要条件或数据时不宣称健康适用；饮食偏好不能覆盖硬限制 |
| D1-08 | **已确认的技术原则**：事实、规则、证据、审核和支持范围按版本关联；来源变更先形成候选，已知失效或撤回的规则停止使用 | 未审核文本与模型提取只作候选；不能回退至已知无效证据。对用户展示粒度和旧收藏提示仍待 OQ-08 收口 |
| D1-09 | **已确认的审核方向**：以风险规则、证据版本及适用范围为主要审核单元；菜谱／变体成分质量与疾病组合支持另行验证 | 专业审核主体和标准尚未落实，研发测试可推进；正式健康能力开放依旧逐项受控。单病种通过不自动扩展到组合 |

第三层另行询问是否以当前已选食材、调料、人数和补买状态，结合推荐/少选/排除筛选已有菜谱；可暂不筛选。此时的aiFoodChoices只存本餐，保存个人设置不自动触发这一步，筛选也不自动保存。关闭健康模式暂停两种AI选择，开始新餐清空本餐选择并保留个人AI去疾。RAG和医学结论边界不变。见[三层流程交付](../ACCEPTANCE-health-workflow-2026-10-27.md)。


### D19-07：账户绑定Key、简化健康入口、健康档案自动保存与建议去重（2026-10-27）

来源：用户要求Key在个人设置填写并随登录保留，可重置清空；去掉健康设置弹框；优化对话语言和界面；健康情况/目标及AI推荐、不推荐食材返回系统随账号保存，并且不再重复用户已有忌口和过敏。此项覆盖D19-04的Key仅页面内存限制、D19-06不保存健康情况/目标/建议的范围及逐轮询问保存建议的冗长流程。

健康入口直接开关。游客需登录；未配置Key引导个人设置，不再显示旧健康设置弹框。对话用简短引导、折叠档案和说明、推荐/少选/建议避开分组、可折叠图鉴与本餐调整。完整对话仍仅页面内存；个人healthProfile保存自述疾病、目标、其他健康关注摘要及最新20项食材建议（含原因/条件），不保存完整消息历史。用户可移除关注项、目标，或清除档案与建议。

### D19-08：三栏接受、个人选择、页内食谱和搭配定位（2026-10-27）

来源：用户要求健康模式开启提示1～2秒自动消失；食材三栏分别提供接受按钮，存入个人设置并供AI读取；食谱直接查看做法，不跳链接；缩短对话到结果的间隔，搭配完成定位菜品。

健康模式开启成功提示1.8秒自动关闭，不自动吞掉其他需要处理的提示。推荐/少选/避开三栏分别接受，存为aiFoodPreferences（各20项）并在个人设置按三类展示、可逐项移除；原始healthProfile.suggestions仍作为档案保留，但不再未经接受直接排序。服务端从账户读取已接受选择随模型上下文发送；普通偏好/旧版写入不得无意擦除该字段，CAS合并不静默放宽避开。健康模式下推荐与少选用于合格候选排序，接受的避开及旧AI去疾取并集排除；本餐偏好不能绕过已接受避开。

AI并列或括号列举的明确食材拆为可匹配项目；提示模型只写单个名称。未知词可接受保存为待匹配参考，清楚标注暂不参与筛选，不凭相似度猜组成或伪造排除。保存、匹配和打开食谱均不调用模型。

食谱示例按真实目录及实际配料匹配，少选作为排序，避开与现有过敏忌口作排除；用卡片直接打开当前页面既有食材/做法弹层。搭配时收起对话、精简健康结果提示和间距；结果DOM提交且busy结束后定位菜品网格（无菜时定位结果说明），保持既有翻页行为，换菜/口味不额外跳位。页面剩余高度不足时以可滚动上限为准，不制造底部空白来凑首行坐标。详见[交付报告](../ACCEPTANCE-health-choices-2026-10-27.md)。
