## 与原型问题的关系

B01～B06 在新 React/Fastify 工程执行了修正后预期的回归，历史 dist 与线上原型没有被修改，旧证据不被覆盖。“新工程回归通过”不等于“旧线上缺陷已部署修复”。图片识别、健康效果、真实账户等没有通过条件的 AC 仍保持未验收。

## 数据保留和运行边界

服务不打印请求正文、限制或模型正文；仅显示本机监听地址。公开 OpenAPI/目录不包含个人数据。前端没有第三方脚本或外链字体。API 使用 no-store。账户长期敏感资料与 Key 的生产路由当前不开放；测试用 AES-GCM 将用户/用途/版本绑定到附加认证数据。

模型操作表保留 expires_at=创建后24小时作为开发去重窗口；没有自动清除旧 ID 的作业，过期不自动重新准入。未知调用保留占额，不擅自按未消费退回。完整保留/过期/清除策略待真实网关收口，不能直接将这个开发值视为批准的上线策略。

## 2026-10-20 人数与20道套餐增量（D7-10～13）

人数参考、上限、模式归一化和自定义错误集中在 `shared/meal-planning.ts`。前端取消自定义时清空提示并重置不再生效的数量；服务端只对启用的自定义校验合计。Schema 的单类数量、已选菜谱和旧结果数组均支持20项，生成的浏览器校验器同步更新。

自动套餐先搜索人数参考范围，再以主料覆盖收益与偏离人数/配比的代价决定是否扩大，最多20道；参考是软目标。严格库存核验之外，重量基准未知但同原料形态/同单位的精确输入可保守约束搭配，不升级为已知净量或足量，仍返回未核实；空白/约量/单位不可比/形态不同不能估算为短缺。自定义+补买走整套餐，不进入六张候选分页，整体至少复用一种已有主料；过敏/忌口照常执行。

大套餐先构造并验证种子方案，再有限搜索。全目录资格检查后，只有相同父菜谱、相同非调料用量/形态/基准和相同缺失调料集合的可选口味才合并为搜索分支；手选和锁定口味保留。类别剩余容量和乐观分数界剪枝不剔除潜在更优解；用量不同的变体另有反例测试。原20,000节点/1,500ms预算不扩大，超限继续如实显示搜索未完成。20道完整套餐、差额18个鸡蛋、单换保留19道通过独立21父菜谱构造目录测试；页面现有17父菜谱不能冒充支持任意20道需求。

手机/桌面人数表、取消自定义、九道补买套餐与20道受理、收藏样式和回归结果见 [本轮验收](../ACCEPTANCE-meal-planning.md)。
