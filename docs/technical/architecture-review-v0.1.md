## 1. 审查结论

**有条件满足进入开发规划阶段的条件。** 现有架构无需重选：模块化单体、关系型事实库、独立规则判断、固定工作流和模型局部提取符合当前产品规模。没有发现必须削减 PRD 功能才能实现的证据，也没有理由引入自主 Agent、多 Agent、独立图数据库或更多常驻服务。

但“所有 FR 都有模块对应”不足以说明执行闭环完整。本轮发现六项需要在相关模块定稿或接入真实数据前解决的设计缺口，包括库存计量基准、召回与业务优先级、本机跨账号隔离、健康规则发布完整性、调用授权绑定及删除恢复流程。开发规划应把它们列为有责任人、验收样例和停止点的任务。

这不是全面开发冻结、云试用或健康开放批准。内容覆盖、免费云、具体模型处理条款、健康审核及运行指标仍按既有门槛验证。未运行实验本身不构成推翻架构的理由。

## 2. 必须解决

### AR-M01｜库存重量与标准配方的计量基准尚未闭合

**证据与影响。** [数据知识架构](data-knowledge-design.md)第 31、49～60 行将标准配方量定义为可食部分量，允许 g／kg 换算，并把形态匹配与库存未知分别表达；[TDD](TDD-v0.1.md)第 111～115、158～169 行没有明确库存毛重、可食净重和配方投料量之间的比较契约。PRD BR-10～13 要求只有可比较的量才能判断足量或缺量。

**触发场景。** 用户输入“带骨鸡肉 600g”，配方需要去骨可食鸡肉 600g。若实现只核对同一食物类别及 g 单位，就可能错误判定足量。重量单位一致并不能证明所计对象与基准一致；这也不能靠“营养仅供参考”消除，因为库存判断是独立承诺。

**建议修改。** 在 M01／M02／M03 的逻辑契约中区分库存测量基准、配方建议投料基准、营养可食部基准及转换依据。仅在对象、形态和基准匹配或有适用换算时比较；基准不明沿用“数量未核实”，不强制新增必填步骤。标准食物的平均可食比例不得自动证明用户实际库存足量。购物缺量必须说明所用基准。

**验证与停止点。** 增加带骨／去骨、带皮／去皮、原料／熟制、同单位不同基准及未知基准案例；验证人数变化和整套累计仍一致。**数量契约与规则定稿前解决。** 受影响文档：数据知识架构、TDD、工作流；继承 BR-10～13、D1-03，不需要削减 PRD。

### AR-M02｜先截断召回、后做业务排序，不能保证“家常优先”

**证据与影响。** PRD BR-20／AC-17 已确认符合条件时家常优先。[RAG 设计](rag-design.md)第 148、160、171～176 行规定业务排序及每路 30→60 扩展，但扩展主要由结果不足或组合失败触发；[工作流](agent-workflow-design.md)第 175 行允许满足输出条件后停止。二者组合后，尚不能保证高业务优先级菜谱进入候选池。

**触发场景。** 同一输入有六道可行家常菜和更多创意菜；创意菜在关键词／向量排名中更靠前，首批已足六张，家常菜落在截断之后。即使在首批内部再做家常排序，也无法恢复未召回的家常菜。这不是尚未确认的“家常与少补买怎样权衡”，而是已确认 BR-20 的执行缺口。

**建议修改。** 首版有限目录优先在结构化合格集合内确定已确认的业务优先层，再在层内用关键词／语义排序；增强路径也可分层召回并记录各层覆盖完成状态。终止条件除了“数量够了”，还须检查必要业务层是否完成处理。若预算不足，不应声称已保证完整业务排序；生产增强可回退结构化路径。未确认的排序权衡仍保持未定。

**验证与停止点。** 增加“首批足六张但高优先级在池外”的对照例，覆盖过滤后补足、翻页及变体归组；小目录以结构化完整结果为参照。**候选排序契约定稿前解决，尤其是启用混合检索前。** 受影响文档：RAG 设计、工作流、TDD；不要求更换数据库或增加模型。

### AR-M03｜本机草稿、账户缓存与跨账号切换缺少隔离规则

**证据与影响。** [基础设施](infrastructure-design.md)第 67～71、83～98 行规定账户隔离、浏览器草稿、登录合并和退出入口；[TDD](TDD-v0.1.md)第 114～120、140～141 行明确服务端身份和本餐版本，但没有定义同一浏览器从账户 A 退出、转游客、再登录 B 时，本机资料的归属与可见性。三层“默认／本餐／演示”隔离不能自动解决“用户 A／用户 B”隔离。

**触发场景。** A 的过敏、疾病或本餐设置仍在浏览器中，B 登录时被当成游客资料显示为待合并，或 A 的迟到请求在 B 页面应用。仅做服务器按用户查询及本餐版本比对，不能完整防止这一问题。

**建议修改。** 本机记录保留明确归属与来源，区分游客原创、账户下载副本和账户内编辑；账户副本不得在退出后自动变成游客可导入数据。身份切换应清理活动内存、取消旧操作，并使结果接收条件包含身份会话代次。只向当前有权访问的身份展示差异；不能先泄露 A 的内容再让 B 确认。具体退出时保留还是清除哪些本机敏感内容，需要补充交互决定，不在本报告代为批准。

同源浏览器存储可被同源脚本读取，不能将 HttpOnly Cookie 或服务器字段加密当成本机数据保护。建议补充安全渲染、CSP、第三方脚本范围、个人响应缓存控制及退出清理测试；账户命名空间能防应用串号，但不能声称抵抗本机访问或 XSS。依据：[OWASP HTML5 存储安全](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#storage-apis)。

**验证与停止点。** 覆盖 A→游客→B、多个标签页、注销后返回页面、离线恢复、迟到结果和游客正常登录合并。**真实个人资料联调前解决，身份／草稿契约定稿时收口。** 受影响文档：基础设施、TDD、工作流；保留游客保存和本机草稿能力，不静默清空 PRD 要求保留的输入。

### AR-M04｜健康支持状态还需绑定完整、不可变的规则发布单元

**证据与影响。** [数据知识架构](data-knowledge-design.md)第 33～41、64～85 行正确地区分未知成分、规则、审核、支持范围和撤回；[TDD](TDD-v0.1.md)第 113、130、155 行要求必要规则全部可核验。但尚未明确：运行时如何知道本次“应该执行哪些规则”，以及疾病支持状态、规则集合、成分完整性与审核签认是否绑定同一发布版本。

**触发场景。** 某疾病仍标支持，而必需规则在导入、关联或更新时漏了一条；执行器仅遍历查到的规则，剩余规则全部通过，于是把“漏执行”误作“全部通过”。另一场景是原内容通过审核后被原地修改，旧审核状态仍被沿用。这里只指出防漏机制尚未明示，不指称现有设计允许模型代替审核。

**建议修改。** 用版本化发布清单绑定适用疾病／组合、必要规则及版本、前置数据、审核记录和覆盖边界；执行时核对预期检查与实际检查，缺规则、缺依赖或版本不匹配均不能返回该范围已通过。成分完整性须对当前限制可判断，不能用一个笼统“无过敏关系”代替。已发布内容不可原地改写；变化形成候选新版，失效独立拦截。

同时补充内容导入、审核签认、发布和紧急停用的操作权限与记录。首版可以使用受控导入工具和人工流程，无需建设复杂管理后台，也不默认要求多位专职审核者；但普通应用写权限不应能直接把候选改成已审核。专业审核资源不足时，正式支持保持关闭，开发测试照常推进。

**验证与停止点。** 用故意漏规则、错误关联、版本混用、审核后改配料、未知复合调味料和撤回回滚做负例；预期全部不能形成未经证明的通过结论。**规则发布契约定稿前设计，正式健康开放前验证。** 受影响文档：数据知识架构、TDD、基础设施、工作流；细化 D1-08～09，不改变健康审核方向。

### AR-M05｜操作 ID、费用选择与实际调用尚未绑定成不可变执行单元

**证据与影响。** [模型服务](model-service-design.md)第 127～146、197～215 行已有身份、费用、型号、配额及共享重试预算；[TDD](TDD-v0.1.md)第 117、127～128、143～147 行已有最少记录、短事务与去重。但是未定义同一操作 ID 携带不同输入／费用／凭证时的行为、尝试准入的唯一性，以及超时后何时释放预留。

**触发场景。** 两个标签页或 SDK 重复提交同一操作，服务端记录已完成但上游状态未知；若重复请求带了新凭证，或重启后把未知调用视为未开始，就可能执行用户未确认的变化或重复占用额度。现有“不自动重试”原则需要由共享状态约束落地，不能仅靠前端按钮禁用。

**建议修改。** 以主体＋操作 ID 定位执行记录，绑定任务类型、规范化输入的受保护指纹、费用方式、供应商／型号、凭证版本及输入输出上限。同 ID 内容变化拒绝或要求新操作；请求正文与敏感普通哈希都不应写入通用日志。尝试认领与预算预留原子执行；未知状态不能被另一执行者自动接管重发，也不能按明确未消费释放费用预留。保存最少状态，不保存个人结果正文。

新操作仍须满足用户／平台总上限。用户主动重试前说明上次可能产生用量；实际请求参数必须符合本次确认的费用路径及上限。可借鉴授权与执行数据绑定、服务端执行状态检查的原则，但无需为每次低额模型调用增加短信或银行式二次认证。[OWASP 操作授权原则](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)

**验证与停止点。** 覆盖同 ID 不同载荷、双实例同时认领、发出后落状态前崩溃、Key 更换、未知超时及预算回收。明确记录保留窗口与过期 ID 的处理。**模型网关契约定稿前解决，真实 BYOK 接入前验证。** 受影响文档：模型服务、基础设施、TDD；不增加自动重试或持久个人结果。

### AR-M06｜删除的持久推进与最新撤销记录仍缺可执行恢复协议

**证据与影响。** [基础设施](infrastructure-design.md)第 135～151 行规定即时禁用、24 小时清除目标、维护清单和每日备份；[TDD](TDD-v0.1.md)第 118、189～195 行要求恢复前有最新清除记录，无法验证时保持隔离。[未决问题](open-questions.md) D5-OQ-03～04、D6A-OQ-03 已承认此门槛。本项是把已有高风险未决项具体化，并非新发现“没有删除设计”。

**触发场景。** 注销请求禁用账户后，认证服务删除失败且实例退出；若维护清单和分项进度只在内存，就无法可靠续办。另一个场景是每日备份后用户删除资料，数据库随后丢失：昨天的删除清单不能证明包含今天的撤销。RPO 24 小时不能被理解为允许复活这一窗口内已删除的数据。

**建议修改。** 清除意图、作用范围及分项状态持久保存，与推荐任务临时上下文分开；按步骤幂等推进认证、资料、收藏及凭证清除，指定重试执行者、频率和超期处理。个人维护场景可先采用 PostgreSQL 中的最少清除记录＋受控维护命令／定期核对，不必引入消息队列。是否能在零费用环境可靠调度，仍需验证。

另明确独立撤销记录的更新时机、持久化确认、序号／覆盖水位和丢失处理。只把记录换个文件名、与业务库一起每天复制，不能证明它是“最新”。恢复若无法证明撤销覆盖，继续保持隔离；完整恢复时间与这一限制共同测量。批准的目标和数据范围继续有效，具体协议待确认后写回设计。

**验证与停止点。** 在每个清除步骤及独立记录持久化边界注入中断，恢复到旧备份并验证删除不复活、任务可续办、处理中状态真实。**账户删除与恢复模块定稿前解决，真实长期资料试用前演练。** 受影响文档：基础设施、TDD；无需改变“不持久保存个人推荐”的决定。

| 编号 | 建议及理由 | 受影响文档／验证方式 |
| --- | --- | --- |
| AR-O01 | 修正“无敏感正文落日志／备份”的歧义。TDD V-09 文字可能被读成禁止备份已授权保存的加密健康资料，与每日账户备份冲突。应区分禁止原图／原始模型正文／明文秘密进入日志或备份，与允许备份授权范围内的应用密文 | TDD 第 9 节、基础设施第 3 节；给出备份允许／禁止字段清单，并实际检查导出样本 |

| AR-O04 | 补充稳定分页与继续查找契约：绑定内容／排序版本和当前条件，定义变体归组、已展示父菜谱、游标失效及会话丢失后的反馈，避免仅有“扩展更多候选”而出现重复页或跳页 | RAG 第 7 节、TDD 第 4～5 节；内容更新、变体重排和重启跨页测试 |
| AR-O05 | 将“一家主供应商＋适配器”的替换演练落成固定契约样本。测试 JSON 合法但漏限制、拒绝、截断、未知用量以及型号别名升级；无需现在接两家生产服务 | 模型服务第 6／8／10 节、TDD V-03；独立标注与固定响应桩，质量标准和真实调用验收分开 |
| AR-O06 | 为来源更新指定维护责任、检查周期及复审触发。当前有版本和撤回机制，但需要有人发现变化；规则集合、模型条款、许可和免费资格可共用轻量维护清单，避免各自造管理系统 | 数据知识架构第 6 节、模型服务第 8 节、基础设施监控；记录检查时间、差异和待处置状态 |

这些建议均未自动升级为已批准决策。AR-O01 是文字消歧，不能借此扩大敏感数据备份范围；AR-O06 不要求对来源变更一律自动停用仍有效的已审版本。

| --- | --- | --- |
| LightRAG、独立知识图谱、健康文档语义问答 | 当前受控菜谱、精确限制及规则取证已有直接路径，额外关系抽取不能替代审核 | 出现明确多跳查询需求，并有可维护关系数据及对照收益 |
| 向量生产化、重排序、HNSW、Embedding 微调 | D2 是实验候选，D3 允许结构化／关键词基线；尚无项目收益和免费运行证据 | 固定测试集显示稳定收益，且能力、费用、地域均准入 |
| 自主单 Agent／多 Agent、跨模型竞速 | 固定任务没有动态规划必要，增加调用、终止及竞态成本 | 新任务无法由当前流程合理表达，且预算内对照证明价值 |
| Redis、消息队列、微服务、长期个人推荐缓存 | 小规模单体尚无容量证据要求；删除记录等可先用现有数据库处理 | 实测瓶颈明确，确有跨进程调度或吞吐需求；另评估保留和费用边界 |
| 高可用多区域、逐卡流式、完整内容管理后台 | 当前邀请试用和完整有效结果发布可先满足需求，投入大 | 规模／可用性目标或内容维护负担有证据增长 |

可推迟的是上述增强能力，真实识别、真实账户、限制执行、口味变体、草稿与健康审核机制仍属于既定功能，不因简化部署而取消。

## 5. 按七个审查方向的判断

| 审查方向 | 判断 |
| --- | --- |
| PRD 重要需求覆盖 | FR-01～12 均有主路径，AC 映射齐全；但 AR-M01～03 表明编号覆盖不等于边界正确。指定荤素汤数量、家常优先、实际换菜、真实登录等不能只按 Demo 验收 |
| RAG／结构化／健康职责 | 主分工正确：主库是真实事实、规则决定约束、检索决定发现与相关性。需解决 AR-M02 的截断覆盖与 AR-M04 的完整规则发布，不建议把健康判断移入向量或生成模型 |
| Agent／循环／延迟 | 首版没有自主 Agent，未见 Agent 过度设计。已定义模型尝试、候选扩展、节点和时间预算；风险在执行器是否真正落实取消及共享预算，按 AR-M05、AR-O02～03 验证 |
| 模型供应商／费用／隐私 | 一家主供应商配适配器是合理折中，人工补录与 BYOK 出口可用。不能保证免费永久或无限，现有文档已承认；实际敏感处理准入和 AR-M05 仍是硬门槛 |
| 营养／疾病风险 | 标准投料参考、缺值不补假数、禁止用展示值证明疾病安全、条件补问及审核门槛均合理。缺口在完整性和执行证明，不建议扩大医疗建议范围；无实质规则及审核材料时不能给健康正确性合格结论 |
| 安全／恢复／测试 | 服务端加密、权限、有限重试、恢复隔离和回归方法方向合理；需补本机身份边界、持久清除推进、最新撤销证明以及具体验收材料 |
| 是否可更简单可靠 | 保留现有单体，先做结构化闭环与受控内容导入；用 PostgreSQL 承担最少预算／清除元数据，人工流程承担小规模治理；减少服务数比另换框架更有确定收益 |

## 7. 进入开发规划的条件与推荐顺序

| 条件 | 审查结果 |
| --- | --- |
| 产品基线及不可放宽规则明确 | 满足；少量产品分支已显式标未定 |
| 核心架构、模块边界与替代路径存在 | 满足；无需重新大规模选型 |
| 每个重要功能有可追踪实现方向 | 满足方向性要求；本报告六项缺口须纳入具体任务 |
| 可用独立样本验证正确性 | 方法已具备；材料准备应成为规划首批交付，不能只检查 Schema |
| 已证明免费云、模型、恢复和健康可开放 | 不满足；这是后续接入／发布门槛，不是禁止制定开发计划 |
| 允许直接认定全设计冻结并承诺上线日期 | 不满足；外部准入和产品未定分支仍影响关键路径 |

建议开发规划按下列顺序安排，并为每项指定负责人及关闭证据：

1. **契约与核心正确性**：M01／M02／M03／M06 先处理 AR-M01、AR-M02、AR-M04，建立可食部、规则漏项和候选截断的独立预期；同时排入产品未定分支的确认任务。
2. **身份、调用与清除**：M04／M05／M08／M09 处理 AR-M03、AR-M05、AR-M06，明确哪些修改涉及交互确认，完成最少元数据和状态转移设计。
3. **本地闭环验证**：以构造或已核验内容完成输入确认、结构化检索、套餐、变体、收藏与恢复；模型契约可使用明确响应桩，不能称为真实识别验收。
4. **条件准入和小规模实测**：分别取得云、模型、身份恢复及内容证据，测完整有效结果及实际资源消耗；混合检索可继续作为独立实验。
5. **受邀试用与健康开放**：按各自门槛逐项决定。健康开发不以专业审核先完成为条件，但正式健康功能开放必须通过审核。

**最终判定：开发规划有条件通过。** 条件是将六项必须解决的问题落实为带验收标准的规划任务，并保留相关模块定稿、真实资料接入与公开健康支持的停止点。本轮不要求重新选择技术栈，也不批准修改 PRD、已确认费用政策、数据保留决定或健康开放门槛。

如后续拟采用的修订会改变退出时的资料保留、产品排序或其他用户行为，先提交影响说明供用户确认；纯技术补齐也应在确认后的修订中保留来源。此报告的建议尚未写回 TDD 或决策日志。
