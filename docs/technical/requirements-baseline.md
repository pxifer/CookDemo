## 2. 已确认功能、流程与交互规则

### 2.1 用户与范围

- 面向独居及 1–4 人家庭的日常做饭场景；允许输入 1–12 位整数人数，默认 1 人。
- 手机优先，兼容桌面浏览器。
- 首版包括真实图片／文字识别、真实账户同步、单菜口味变体及受审核条件约束的健康能力。
- 使用可核对的菜谱集合及变体，不开放集合之外不受约束的新菜生成。
- 首版不维护多位用餐者档案，不加入儿童份量、食量系数或个人减脂／增肌营养目标。

依据：DR-01、DR-05～08、DR-12；PRD 第 2、3 章。

| 能力 | 已确认要求 | 主要追踪 |

| 单菜口味 | 全局口味为默认，单菜手动选择优先；变体主料不变，可改辅料、调料、用量和步骤；限制、库存、差额及营养同步复核 | FR-08；BR-22～23 |

鸡蛋本身不使素菜变为荤菜；汤按菜品分类，不能仅凭含蛋或有汤汁判断。自动三道的具体配比仍未确定。

所有已确认限制须贯穿推荐、单换、重推、口味变体和收藏复查。不检查调味料库存，不等于停止检查其中的过敏或忌口成分。

### 2.3 核心流程

普通流程：

进入／恢复本餐 → 图片或文字输入 → 分类提取 → 用户核对及冲突处理 → 设置人数、口味和库存策略 → 推荐 → 单换／重推／变体／详情 → 收藏或主动保存默认。

健康分支：

主动开启 → 登录并保留本餐输入 → 核对疾病名称 → 检查已审核支持范围及当前条件 → 展示有依据的结果，或停止健康推荐并提供修改／普通模式出口。

提到疾病不自动开启健康模式。切回普通模式保留本餐信息，过敏与明确忌口继续生效。

### 2.4 必须区分的未知状态

| 状态 | 行为 |
| --- | --- |
| 食材疑似 | 保留待处理，不参与；可用其他已确认食材继续 |
| 数量空白、约量、单位不可比 | 允许推荐，相关食材及结果标“数量未核实”，不暗示足量 |
| 过敏、明确忌口未知，或限制无法分类 | 暂停推荐，定位待处理项；不能自动忽略或显示已生效 |
| 健康项目未支持或约束无法满足 | 停止健康推荐；由用户主动修改或返回普通模式 |
| 营养或依据不足 | 不补假数、不编引用、不输出确定性适宜结论 |

### 2.5 数据作用范围

- 长期资料：主动保存的限制、偏好、默认设置及确认保存的疾病资料等；账户支持跨设备同步。
- 本餐草稿：文字食材、可选用量、人数、本餐设置及确认状态；首版保留本机。
- 收藏：菜谱与口味，不是固定旧人数的整餐快照。
- 演示：独立临时上下文，不写入真实资料或草稿。
- 开始新一餐：清空本餐并加载默认，保留资料与收藏，默认仍只应用本人限制。
- 清空 Demo：明确确认后清除相应演示数据；不能自行扩大为云端删除或账户注销。
- 原图：不长期保存；短期处理和删除上限仍待确定。

## 4. 对技术专题的直接影响

以下是需求对设计的约束，不代表已经选定实现方式。

| 专题 | 必须解决的问题 | 尚未确定的实现 |
| --- | --- | --- |
| RAG／检索 | 有限内容包、菜谱与变体边界、来源追溯、支持覆盖及失效处理；检索命中不能代替限制和数量核对 | 是否需要 RAG；普通检索、向量、图或混合方案；不预选 LightRAG |

健康审核机制应预留扩展点。审核资源未落实不阻塞健康专题设计与开发；测试状态不能被呈现为已审核的正式能力。

## 5. 阶段结论与验证继承

目前未发现需要推翻已确认产品范围的冲突。主要问题是未决分支未闭合，以及原型尚未满足正式要求。

以下属于已解释的历史差异：

- README 曾称人数与菜数上限未确认；PRD 已确认 1–12 人、1–6 道。
- 原评审的补买复用、附加清单问题，已由 PRD 收口。
- Demo“图片不会上传”只适用于模拟实现，不能作为正式处理承诺。
- 健康“审核后开放”与本轮“审核不阻塞开发”分别约束发布和研发，二者可以同时成立。
- PRD 页首“待审核”不撤销用户本次指定其为需求基线。

后续验收继承 PRD AC-01～AC-32，并补充本轮决定的场景：

1. 未知明确忌口和无法分类限制暂停推荐，原限制保留。
2. 游客本机收藏菜谱及口味，登录后按确认结果同步。
3. 游客主动保存默认，登录差异确认不丢本餐条件，不静默覆盖硬限制。
4. 敏感数据处理链路满足境内约束。
5. 未审核健康数据可用于明确标识的开发测试；正式开放状态独立受控。

本轮完成的是文档、规则及证据核查，未执行正式功能测试、代码修复或重新部署。
