# main-v70：单菜理由去重、食材恢复大类

2026-11-14 00:5x 更新既有 CloudBase HTTP 函数成功。

## 1. 食材下拉恢复大类

按你的澄清：大类仍是肉禽、鱼虾海鲜、蛋类、蔬菜、菌菇、豆制品、主食杂粮、奶类、水果、豆类坚果、其他食材；不再拆“鱼类/虾类”等小类。但列表仍只包含 **1000 道已发布菜谱里真实作为主料/辅料使用** 的食材，腌料/调味料不进入。

## 2. 单菜理由不再千篇一律

之前每张卡都写“用上现有西红柿、鸡蛋。含你优先选择的鸡蛋、西红柿。”v70 改为：

`菜品类别，做法，以主料为主。` + `含你优先的 X。`（只提一个命中的优先/少选食材）

例如三道菜会分别以“汤品，煮制，以乌冬面为主”“荤菜，炖制，以猪肉为主”“素菜，炒制，以鸡蛋为主”开头，不再共用同一句。

若用户有接受记录但本菜未命中，明确写“没有命中你标记的优先或较少食材”，不再退回“无法判断”。

## 3. 业务链路的真实缺口

- “维生素D不足”是营养指标，不是疾病/目标主题；对话能给营养参考，但选菜没有对应疾病级依据。
- “瘦身”能映射减脂，但知识事实需要成年人、运动情况等条件；当前档案未确认，因此没有逐菜依据。
- 用户接受的食材选择是**食材级**的，程序已用于排序和单菜理由，但它不是疾病级逐菜证据；像低脂牛奶、无糖酸奶这类接受项在菜谱里没有对应食材时，无法“落到菜品”。

因此本版解决的是：有接受记录时给出食材级判断、理由具体化；**没有**把营养指标/未确认条件包装成疾病结论。要真正让疾病/目标到菜品链路稳定，还需要下一步补目标级菜品规则或确认条件。
