# main-v58：纠正补买规则、压缩提示与知识耗时实测

2026-11-13 北京时间 21:20 更新既有 CloudBase HTTP 函数成功。v58 修正了 v56 对“允许补买”模式的误改，并把模型提示压缩为“主料 + 做法类型 + 两步摘要”；函数超时 60 秒、知识引用与 1000 菜谱不变。

## 规则纠正

- **不允许补买**：AI 按人数参考（含荤素汤）或自定义数量出餐，1 人 3 道、2 人 5 道，不再固定 6 道。
- **允许补买**：保留“以现有食材为基类”的候选浏览，每页 6 道；健康模式再叠加饮食档案、推荐/不推荐食材等限制。v56 曾把健康模式强制为一餐，属于规则误改，v58 已撤回。
- 因此“6 道”只应出现在允许补买的候选浏览；如果关闭补买仍看到 6 道，请强制刷新确认新版本。

## 时延定位（实测）

用线上公开知识（只读 Data API，不涉及个人 Key）测得：

| 环节 | 结果 |
| --- | --- |
| 知识 payload 大小 | **2,031,671 字节（约 2.0MB）** |
| 首次 prepare（含下载、完整性 hash、校验、provider 构建） | **约 1.10s** |
| 同实例再次 prepare | **约 84ms** |
| 每次 assertCurrent（校验撤回） | **约 66–75ms** |
| 单次选菜知识读取（v57 起） | 2 次（prepare + 返回前） |

结论：知识库变大带来的是**冷启动约 1 秒、热请求约 0.15 秒**，不是 7–8 秒的主因。主要耗时在模型：此前提示最多 12 道菜谱的**完整做法**（约 10k+ 估算 token），模型再生成 6 道理由。

## 本次压缩

- 提示中的菜谱改为：主料名单、做法类型（蒸/煮/炒/煎炸/烤/凉拌等）、前两步各 ≤70 字摘要；完整做法只在服务端绑定证据与页面展示，不再进模型。
- 12 道候选的提示估算从约 10k+ token 降到约 5–7k（含系统提示）；理由限 80 字、摘要 160 字，输出上限随菜数伸缩。
- 未降低过敏/忌口/补买/数量等硬条件，也未删知识。

## 验证

- 单元 **410 项 / 408 通过 / 2 跳过 / 0 失败**；两套类型、Vite 构建通过。
- 回归：不允许补买 1 人自动 3 道；2 人自定义 1 荤 1 素 2 道；允许补买仍 6 道/页并可翻页。
- 线上：`/healthz`、`/readyz` 200；首页 `index-a0MDwe2s.js` 与本地一致；函数 `Timeout=60`。

## 边界

真实模型时延仍未测（无法在不关闭 Edge 的情况下读取其 Cookies；未伪造登录或借用其他 Key）。若压缩后仍超过 4 秒，下一步只能继续压系统提示/输出或更换生成策略，需要一次真实分段计时。
