# 食材大类匹配验收

日期：2026-10-23。依据用户对“猪肉、白菜、粉条”无法召回白菜猪肉炖粉条的反馈；设计边界见 [D13-06](../product/decision-log.md)。

后续用户要求统一优化所有食材简名输入，已扩展名称包含匹配并完成真实4176桌面/手机测试。下文的早期运行环境判断及“没有库存但未知量仍未核实”行为，以[后续修正验收](ACCEPTANCE-simple-ingredient-input-2026-10-23.md)为准；历史证据保留。

`local-business-gallery-v1` 运行视图可识别独立输入“粉条”，并将其按大类匹配到菜谱中的“土豆干粉条”。用户输入“猪肉、白菜、粉条”可召回“白菜猪肉炖粉条”：猪肉匹配五花肉，白菜沿用“大白菜”现有精确别名，粉条匹配具体粉条来源。大类记录只允许参与推荐和主料复用；具体部位/形态及原方缺少用量仍显示未核实，不伪造库存量、足量或补买差额。

工作台大类词典明确覆盖猪/鸡/牛/羊肉部位、鱼虾、土豆/小土豆及粉条/粉丝。已覆盖的排除例包括猪肉不匹配牛肉、粉条不匹配米粉，以及鱼类/虾类调味或加工品不因字符相同自动归类。未核验候选配方遇过敏或忌口仍按现有逻辑保守排除。

验证：`npx tsx --test tests/domain.test.ts tests/gallery-content.test.ts`；覆盖完整图鉴数据中的目标菜、文本输入识别、库存核对状态、大类范围与不匹配负例。

实际页面复测补充：用户截图中的提示来自菜谱请求校验。输入词条有意使用`form: unspecified`，但工作台Meal schema只允许`raw/cooked/bone_in/skin_on`，服务因此把请求拒绝为`INVALID_REQUEST`。现在schema和生成的浏览器校验器都接受`unspecified`；API回归测试以“猪肉、白菜、粉条”提取结果构造确认食材并提交推荐请求，验证服务不再返回400。此前复测还发现4176运行中的API是旧进程，目录里没有运行时“粉条”记录；尝试用项目本机业务脚本在4180启动新版服务时，启动检查返回`DATABASE_SCHEMA_OR_CONNECTIVITY`，本执行环境没有已连接的应用终端可重启4176进程，未修改数据库。要让截图对应的4176服务加载此修复，仍需重启其后端进程。

该词典是本机推荐召回层的显式类别规则，不是正式食品标准、营养/过敏数据、候选原方审核，也不把类别兼容升级为可互换或精确库存换算。

## 截图问题复测补充

截图中的问题有三处：服务返回的`unresolved`食材在当前词表中能识别时没有由前端再核对；剩余未知文字被错误地转换为`unclassified`忌口，导致整批推荐暂停；候选菜谱虽已召回，但仍按家常标签而非食材命中度排序，完全对应的菜可能落到后页。另一个截图中的`INVALID_REQUEST`由当时运行中的服务仍使用旧Meal schema导致，形态`unspecified`未获接受；源码schema和生成校验器已加入该形态，但已运行服务需重启加载。

修复后，浏览器用当前内容词表复核未识别片段；能识别的词条正常进入食材清单，未知片段保留为可编辑的待识别食材，不参与匹配且不变成限制。只有识别结果中的明确过敏/忌口继续进入硬限制。更多菜谱模式按命中的必需主料数、覆盖率及精确命中数排列，不删除其他合格候选。

验证：基于项目实际145道图鉴构造截图中的“鸡蛋、牛肉、猪肉、白菜、粉条”旧识别返回（将粉条模拟为`unresolved`），完整经过前端归一、工作台推荐和分页排序后，“白菜猪肉炖粉条”出现在第一页；所有符合项仍可翻完分页，候选集没有被裁掉。具体五花肉和土豆干粉条的数量状态保持未核实。`npm run build`、`npm test`通过；全量91项中90通过、1项跳过（需本机PostgreSQL）。当前执行环境没有4176监听服务，因此没有做浏览器实时复测；如用户本机仍运行旧后端进程，需重启以加载源码修复。
